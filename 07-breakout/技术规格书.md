### 3.1 ★ 本作**不使用任何物理节点**（有意的、已记录的偏离）

pong 的样板里实体根是 `Area2D`（`monitoring`/`monitorable` 全关，只当几何持有者），那是**沿革**。本作**一个 `Area2D` / `CollisionShape2D` 都不建**：

- 本作的碰撞是**解析扫掠**（见 §5），全程不向物理服务器查任何东西；
- 挂一个永远不查询的 `Area2D` 是纯粹的仪式成本，还会给人"这里有物理检测"的错觉；
- 三面墙**本身就不是节点**：它们是三条边，用 `Polygon2D` 画出可见边框，碰撞判定走矩形（§4）。

**判定依据**：CONSTITUTION 五点五要求的是"**有明确功能语义的引擎节点**必须显式建在场景里，不得用代码造等价物"。扫掠圆-矩形求解器**引擎里没有对应的节点**，而本作也确实不需要任何物理查询，所以没有"该用而没用"的引擎节点。**若用户认为该与 01 保持完全一致，改回 `Area2D` 只是加一层壳，随时可改。**

### 3.2 节点访问

一律 `@onready var _x: Type = $Path`（CONSTITUTION 五）。

## 4. 场地几何（`breakout_field.gd`，`class_name BreakoutField`）

`configure(field_cfg, ball_radius)` 在启动时算定：

- `SIZE = (1280, 720)`。
- `LEFT / RIGHT / TOP`：可弹跳区域的内边界（`margin_x` / `wall_top`）。
- `wall_rects() -> Array[Rect2]`：**左、右、上三面墙各给一个矩形**（厚度 `wall_thickness`，位于内边界之外）。之所以用矩形而不是解析平面，是为了让墙和挡板、砖块**走完全同一条 `_sweep_rect` 代码路径**——只有一种碰撞形状，没有第二套逻辑要维护。
- **底边不是墙**：球心越过 `SIZE.y + radius` 即判掉球（见 §6）。
- 砖块网格：`cols` 列、行数 = `brick_scores.size()`；砖宽由 `(RIGHT - LEFT - (cols-1) * brick_gap) / cols` **推导**，不手填，改列数或边距时自动跟着变。原点 `(LEFT, TOP + brick_top)`。

## 5. ★ 碰撞：扫掠解析解（复用 01-pingpong）

`ball.gd` 的 `_sweep` / `_sweep_rect` / `_clip_axis` / `_push_out_of_overlaps` **照搬 `01-pingpong/scripts/ball.gd`**（DECISION_LOG 013 立下的方案），只把"固定四个碰撞体"换成"一份动态碰撞体列表"：

- **每物理帧**：先 `_push_out_of_overlaps()`（运动的挡板可能把球挤进体内），再 `_sweep(velocity * delta)`。
- `_sweep`：循环至多 `MAX_BOUNCES` 次——取**最早接触**的 `t`，走到接触点、按接触法线反射、用**剩余距离**沿新方向继续走。**任何速度都不穿隧**，且墙-挡板-砖块的夹角取的是真实接触面。
- **接触法线**由 slab 决定：横向 slab 命中 → 水平法线；纵向 slab 命中 → 垂直法线。**砖块拐角处的反弹因此是对的**，不用写特例。
- `_earliest_hit` 的候选集合 = `BreakoutField.wall_rects()` + 挡板矩形 + **`Bricks` 下所有未碎的砖块矩形**。
  - 砖块若在同一次 `_sweep` 里被打碎，**必须立刻标记**（`BreakoutBrick.break_brick()` 置位），球的候选集合跳过已标记的砖——否则 `queue_free()` 要到帧末才生效，同一块砖会在这一帧里被反弹两次。
- **速度**：每次击中挡板 `speed *= 1 + speed_boost_per_hit`，上限 `max_speed`；过关再乘 `speed_step`（`level_speedup_cap` 封顶）。
- **最小仰角**：`_enforce_min_angle()` 把方向拉回"与**水平**方向锐角 ≥ `min_angle_from_horizontal_deg`（默认 22°）"——砖块可以被打飞的球贴着左右墙做水平往返，永远打不到上面，这一条是防死局的**不变式**（注意与 pong 相反：pong 防的是近垂直，这里防的是近水平）。
- **挡板手感**：命中挡板**上表面**（`normal.y < 0` 且 `|normal.x| < 0.5`，即前脸）时，法线绕轴旋转 `paddle_curve * edge`（`edge = clamp((ball.x − paddle.x) / half_width, ±1)`）再叠加 `random_deflect_deg` 随机角；并**强制 `velocity.y < 0`**，防止旋转把球压回挡板里。其余接触面（砖块、墙、挡板侧面）都是纯镜像。

## 5.1 瞄准扇形（`aim_guide.gd`，`class_name BreakoutAimGuide`）

**要解决的问题**：玩家其实一直有主动权（有充足时间把挡板摆到任意接触点，见 §5），缺的是**看见"接触点 → 出球方向"这个映射的手段**——出球方向同时取决于接触点与来球角度，玩家算不出来，只能试。扇形补的就是这件事。

- **`BreakoutBall.paddle_return_direction(paddle, jitter) -> Vector2`（新增，公开）**：算出"打在挡板这个位置会往哪走"。
  - ⚠️ **它与真实反弹共用同一个函数**：`_bounce()` 里挡板正面那一支现在就是调它（`jitter` 传随机抖动），**扇形传 0**。这样"预测"不可能与"实际"漂移——这是本作最重要的一条不变式，断言里直接比对了 60 组（**60/60 完全一致**）。
  - 同一次重构把 `_enforce_min_angle()`（原地改 `velocity`）拆成了**纯函数 `with_min_angle(direction)`**，好让预测侧也能用它。`launch()`、`_set_direction()`、`_push_out()` 都改走这个纯函数。
- **形状**：以**挡板顶边中点**为顶点、向**上半平面**张开的一个小扇形（半径 `radius`）。
  - **两层**：外圈用 `alpha`（"也可能在这片里"）、内芯覆盖 `core_ratio` 的角度用 `core_alpha`（"多半在这附近"）。**这就是让张角读起来像"不确定"而不是"测量值"的关键**。
  - **画不出水平线以下**：`set_fan()` 把两端都 clamp 到 `[-π, 0]`。真实反弹恒向上（§5 的最小仰角），扇形越过水平只会**夸大**不确定性。
- **模糊程度 = 球到挡板的曼哈顿距离**（`|Δx| + |Δy|`，按用户要求）：`half_width = lerp(min_spread, max_spread, clamp((gap - near) / (far - near), 0, 1))`。
  - 球近 → 收到逼近一条线；球远 → 张开。**远的时候模糊是诚实的**：它可能先蹭墙或蹭砖，方向本来就不确定。
  - `min_spread_deg` **必须 ≥ `random_deflect_deg`**（断言钉住）——扇形永远不比真相更窄。
- **只在球下落时显示**（`velocity.y > 0` 且 `is_in_play()`）：那才是"正在决定接触点"的时刻。`aim_guide.enabled=false` 可整体关掉，回到原版的盲打。
- **职责**：`AimGuide` 只管画——顶点、中心角、半张角都由 `game.gd` 推入；**它自己不算任何与球有关的东西**，所以它不可能偷偷不同意那次反弹。

## 6. 对局（`game.gd`，`class_name BreakoutGame`）

状态机 `State { TITLE, READY, PLAYING, DYING, LEVEL_CLEAR, OVER }`：

- `TITLE`：棋盘就位（砖块已排好）、球吸附在挡板、显示标题，空格开局。
- `READY`：球**吸附**在挡板上随挡板移动（玩家可以先把挡板挪到想要的位置），显示 `PRESS SPACE TO LAUNCH`，空格发球。
- `PLAYING`：球自主运动；`_check_ball_lost()` 每帧判球是否越出底边。
- `DYING`：掉球后的短暂停顿（`life_pause`）。
- `LEVEL_CLEAR`：砖块清空后的停顿（`level_pause`），随后重建阵列、`level += 1`、提速。
- `OVER`：命耗尽，显示分数与最高分，空格重开。

**吸附**：`ball.attach_to(paddle, offset)` —— 球每帧跟随挡板；`ball.launch(min_deg, max_deg)` 才真正开始运动。

**挡板控制**（两种输入并存，谁最后动谁说话）：
- 键盘：`wasd_left/right` 或 `arrow_left/right` → `paddle.set_direction(-1/0/+1)`，速度限幅、限位。
- 鼠标：收到 `InputEventMouseMotion` 就把挡板切到"跟随鼠标 X"模式；**任何一次方向键按下就切回键盘**。鼠标跟随用 `paddle.get_local_mouse_position().x`（Node2D 自带的方法，已处理好 `canvas_items + keep` 的拉伸变换，不需要自己推坐标空间）。

**计分**：按砖块所在行取 `brick_scores[row]`。`_best` 本次运行内取最大。**不加命**（见策划案非目标）。

### 6.1 连击

**动机**：砖层后面有一条窄缝（墙与残砖之间），球会在里面**反复快速横跳**。那段既打不到东西也没风险，是纯死时间。连击把它变成高光。

- `_combo` = **从上次碰到挡板起碎掉的砖数**。每次 `_on_brick_hit` 加一。
- **倍率**：`clamp(1 + (combo - 1) / combo_step, 1, combo_max)`——前 `combo_step` 块按面值，之后每 `combo_step` 块抬一档，封顶。**得分 = 行分 × 倍率**。
- **音高**：`min(1 + (combo - 1) × combo_pitch_per_hit, combo_pitch_max)`，作为 `AudioStreamPlayer.pitch_scale` 传给击砖音——长连击听上去就是一段上爬的音阶。
- **清零点**：碰到挡板（`_on_paddle_hit`）、新球/过关（`_enter_ready`，它同时覆盖这两种）、回标题与开新局（`_enter_title` / `_start_run`）。**"别让球回来"就是连击的代价。**
- **HUD**：倍率为 ×1 时徽章**不显示**——它只在真的开始给钱时才说话，不跟常驻读数抢位置。

### 6.2 鼠标点击 = 空格

`_unhandled_input` 里除了切换指针模式，还接住左键单击，**在标题/结算页开始或重开、在待发状态发球**。游玩中单击不做任何事。
- **为什么走 `_unhandled_input` 而不是 `_gui_input`**：本作根 Control 是 `mouse_filter = IGNORE`（§3.1 说明过），这样鼠标**移动**事件才能到 `_unhandled_input` 去切换指针模式；单击走同一条路，不必为了点击把根改回 STOP 而冒"移动被 GUI 吃掉"的风险。
- **同一条规则也补到了 `06-simon` 与 `09-lights-out`**：它们都吃鼠标，标题页（西蒙还有结算页）因此也接受单击开始。

## 7. 配置 `breakout.cfg`

**完整取值与注释以 `07-breakout/breakout.cfg` 为准**（唯一可信源）。分区职责：

| 分区 | 关键项 | 职责 |
| --- | --- | --- |
| `[field]` | `bg_color` `wall_color` `ball_color` `paddle_color` `margin_x` `wall_top` `wall_thickness` `brick_height` `brick_gap` `brick_top` `cols` `brick_colors`（N 元数组）`brick_scores`（N 元数组）`row_tones`（N 元数组） | 配色、场地内边界、砖块网格、每行的颜色/分值/音高 |

## 8. 砖块（`brick.gd`，`class_name BreakoutBrick`）

- 场景：`Brick`(Node2D) > `Face`(ColorRect)。
- `setup(rect: Rect2, color: Color, row: int, score: int)`：按矩形摆好 `Face`，记下行号与分值。
- `global_rect() -> Rect2`：给球的扫掠用。
- `break_brick() -> bool`：置"已碎"并 `queue_free()`；**重复调用返回 false**（同帧被球和别的东西碰到时只算一次）。
- `is_broken() -> bool`：球的候选集合按它过滤。

## 9. 只读叠加层（`breakout_debug.gd`，`class_name BreakoutDebug`）

- **`P`（`debug_toggle`）**：画球的**碰撞圆**与**速度矢量**、挡板的矩形轮廓、以及可弹跳区域的**内边界矩形**。用来回答"为什么这一球这么弹"。
- **全部用一种高对比亮黄 `FFE066`**，不用各自的实体色：轮廓是用来**描述**实体的，用实体自己的颜色画就会消失进实体里（挡板轮廓是挡板色、活动区轮廓是墙色，实测都看不见）。
- ⚠️ 开关**必须"出去也重绘"**（`_draw` 的绘制命令会被画布缓存）——**直接照抄 `03-pacman/scripts/pacman_debug.gd` 的带 setter 写法**（DECISION_LOG 029）。

## 10. 程序化音频（`breakout_audio.gd`，`class_name BreakoutAudio`）

启动时合成 PCM 到 `AudioStreamWAV`（22.05kHz / 16-bit / 单声道），`AudioStreamPlayer` 池播放。

| 事件 | 音色 | 触发 |
| --- | --- | --- |
| 击砖 | 方波 0.07s，**音高取 `audio.row_tones[row]`** | 砖块被击碎 |
| 击中挡板 | 方波 320Hz / 0.06s | 球与挡板接触 |
| 撞墙 | 方波 200Hz / 0.05s | 球与三面墙接触 |
| 掉球 | 下行三音 | 球越出底边 |
| 过关 | 上行三音 | 砖块清空 |
| 发球 | 方波 300Hz / 0.10s | 空格发球 |

合成 helper（方波 / 扫频 / 音阶 / 包络）与 01–06 同源，**后续可整体抽到 `plugins/`**（DECISION_LOG 015 备注，时机由用户定）。

## 11. 输入

复用项目级 `[input]`（`project.godot` 已定义，本作无需新增）：`wasd_left/right`、`arrow_left/right`、`fire`（空格）、`debug_toggle`（`P`）、`cheat_toggle`（`[`）、`ui_cancel`（Esc）。

- 左右意图 = `wasd_left || arrow_left` / `wasd_right || arrow_right`（fallthrough 合并）。
- 键盘走 `_process` 轮询（`Input.is_action_pressed`）：挡板是**持续按住移动**的，不需要事件顺序。
- 鼠标走 `_unhandled_input` 的 `InputEventMouseMotion`——只用来**切换控制模式**，位置仍从 `get_local_mouse_position()` 取。

## 12. 风险 / TODO

| 事项 | 优先级 | 说明 |
| --- | --- | --- |
| 砖块与挡板的夹缝 | 中 | 球落在挡板与砖块之间的窄缝里可能连续反弹，靠 `MAX_BOUNCES` 兜底；实机确认不会"卡在缝里抖动" |

### 实拍与断言暴露并修掉的问题

- **挡板是白的**：`paddle.gd` 摆了 `Face` 的尺寸却**从没给它上色**，`paddle_color` 一直没被用上。已在 `setup()` 里接收并把颜色交给 `Face`。
- **调试叠加层看不见**：原设计"用实体自己的颜色画它的轮廓"，结果轮廓和实体糊在一起（挡板轮廓是挡板色、活动区轮廓是墙色）。改成**全部用一种高对比亮黄** `FFE066`——轮廓是用来"描述"实体的，用实体的颜色画就消失了。
- **水平球会被往下方掰**：`_enforce_min_angle()` 在 `velocity.y` 恰好为 0 时把符号取成 +1，即把球推**向下**。真实对局不会产生严格水平的球（发球是陡角、反弹保持 `|v.y| ≥ sin(min)`），所以平时碰不到；但只要碰上就是"球莫名其妙往挡板扎"。改成**朝上**——水平球没有竖直动量可保，向下则毫无道理。断言里专门留了一条钉住它。
- **重建棋盘时旧砖没离开碰撞集**：`_build_bricks()` 用 `queue_free()`，而释放要到帧末才生效，于是新一帧里球仍会撞到已下场的旧砖。改为 `retire()`：**立刻**标记出局并隐藏，再 `queue_free()`。砖块的标志位也从 `_broken` 更名为 `_out_of_play`，把"被打碎"和"被换掉"这两种出局统一到一个概念下。

### 修过的

- **鼠标控制球拍用错了坐标系**（用户实机发现：未发球时球拍剧烈抖动，且鼠标到不了右半场）：
  - 原实现是 `_paddle.follow_pointer(_paddle.get_local_mouse_position().x)`。**`get_local_mouse_position()` 给的是相对球拍自己原点的坐标**，把它当**绝对目标**喂回去就形成了回路：`target = 鼠标世界 x − 球拍 x`，于是球拍收敛到 `鼠标 x / 2` ——鼠标推到 1100，球拍只到 550，**右半场永远够不着**；逼近过程中两侧来回抢，就是那个抖动。
  - 改为 **`get_global_mouse_position().x`**（世界坐标，与 `position.x` 同一空间）。
  - **教训**：`get_local_mouse_position()` 确实"已经处理过拉伸变换"，但它给的是**局部**坐标而不是世界坐标——**"处理了变换"不等于"和 position 同空间"**。
  - 验证用真实光标做的：`Window.warp_mouse()` 把光标推到 1100 / 150 / 1279，球拍分别落在 1100 / 150 / 1170（最后一个被墙面夹住），**静止时漂移 0.000 px**。这类"鼠标在哪个坐标系里读"的问题断言套件覆盖不到，只能靠真窗口跑。
