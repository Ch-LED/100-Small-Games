## 4. 物理与运动模型（本作的成败点）

### 4.1 球的节点配置

| 属性 | 值 | 说明 |
| --- | --- | --- |
| 节点类型 | `RigidBody3D` | 用户选定：走 Jolt 真模拟（DECISION_LOG 054） |
| `continuous_cd` | **`true`（必做）** | 快节奏 + 薄路面 = 隧穿的标准配方。**这一项漏了球会直接穿过赛道掉下去。** |
| 碰撞形状 | `SphereShape3D`（**图元**，不是 mesh 碰撞） | Jolt 对球体图元的求解比 trimesh 稳得多，这是选 Jolt 能拿到的实际红利。 |
| `physics_material_override` | `PhysicsMaterial`：`friction` / `bounce` 从 cfg | |
| `linear_damp` / `angular_damp` | 从 cfg | Jolt **没有滚动摩擦**，球在平地会永动；衰减主要靠这两个（见 §4.2）。 |
| `mass` / `gravity_scale` | 从 cfg | |
| `contact_monitor` / `max_contacts_reported` | 需要接触信息（滚动音、尘、拖痕）时才开 | 开着是纯开销。 |

### 4.2 ⚠️ 三个必踩的坑，动手前先记住

1. **`PhysicsMaterial.rough` 是 Godot Physics 专用的滚动阻力开关，Jolt 大概率直接忽略。** 不要指望它，也不要因为"设了 rough 还是永动"而困惑——滚动阻力要靠 `angular_damp` / `linear_damp` 与自定义力矩来凑。**这条要在 Phase 0 实测确认**，结论出来前文档里不许写成"已解决"。
2. **转向响应是涌现的**：给的是扭矩，出多少角速度、多少线速度，取决于摩擦系数、质量、惯量、接触点法线。**这条曲线必须先量出来**，否则后面所有关卡都建在没量的地基上（Phase 0 的全部意义）。
3. **赛道不能是零厚度的薄壳**：`ConcavePolygonShape3D` 没有厚度，球高速下会从边缘钻过去。扫掠横截面时要生成**有厚度的实体**（§5.2）。

### 4.3 驱动

主驱动是**真扭矩**：每物理帧在 `_integrate_forces(state)` 里，把键盘的二维输入解算成**基相对**的期望自转轴，`apply_torque(axis * spin_torque)`，其余交给 Jolt 积分 + 接触摩擦。

**下压力（2026-10-12 追加）**：抓地上限从 `μ·m·g` 改成 **`μ·(m·g + k·v²)`**，`k` 是 cfg 的 `downforce_coefficient`。像赛车的翼片——越快压得越紧，于是快速球能守住慢速球守不住的线。

⚠️ **它进的是摩擦上限，不是往球上压一个力**。地面是解析约束（§4.4），球**已经被钉在离路面恰好一个半径**的地方，再压也没处压；下压力真正买到的东西是**抓地**，而抓地就是在这儿定的。飞行模式（`gravity_scale = 0`）不走 `_ride_road`，所以自动不受影响。

**⚠️ 预批准的后备方案**：若 Phase 0 实测发现涌现响应不可控（响应过慢 / 过非线性 / 随摩擦系数剧烈变化），**退到"每帧把 `angular_velocity` 朝目标方向拉"的助力模式**——仍是 `RigidBody3D`、**仍走真实接触摩擦**，只是自转被直接驱动。二选一由 Phase 0 的实测数据决定，届时记入 DECISION_LOG。

### 4.4 地面是**解析的**（2026-10-10 追加，推翻 055 的地面部分）

**物理世界里没有地板。** 每物理帧由 `ball.gd::_ride_road()` 从赛道算：

1. 把球放回**路面之上一个半径**处（以路面为基准：`路面点 + 面内偏移 + 法线 × 半径`）；
2. 禁止它朝路面里运动（抹掉法线方向的**向内**速度）；
3. 用一条**自写摩擦**抵消接触点的滑移。

**摩擦必须一起接管**：接触摩擦就是接触本身，没有碰撞体，驱动的扭矩只会让球原地空转。规则**照抄 Jolt 用的那条**——滑移被反向冲量压制，上限 **`μ · m · g`**，也就是当初标定的抓地上限。所以这不是重新发明手感，是把同一个规则搬到解析侧。

**为什么不是"给球一块地板"**：扫掠出的路面是**折线**，每道接缝都是折痕，球过折痕被踢。而任何"在球下方**移动**的碰撞体"都会往球上传东西——跟随的平板试过两种动法，`sync_to_physics` 打开时传运动（平板跟着球下沉就把球拽下去），关闭时传穿透冲量（1 米的板穿、20 米的板把球弹飞 19 米）。**静止的折线路面虽然粗糙，至少不传任何东西；解析地面则连折痕都没有。**

**实测**（`away` = 朝外的法向速度 RMS，也就是"看得见的颠"）：

| | away RMS | 极速 |
| --- | --- | --- |
| 路面碰撞（Jolt） | 0.2358 | 19.5 |
| 路面碰撞 + `ground_glue` 补丁 | 0.0754 | 19.5 |
| **解析地面** | **0.0006** | **20.2** |

另外：停在路面上 **+0.500 m**；越过**半宽**即不再提供支撑，球掉下去（这就是"掉出赛道"）。

⚠️ **滑移比读作 1.162 而非 1.000**，且摩擦系数 1.2→6.0 对它**毫无影响**——说明它不是摩擦限的。**未能确认这是真打滑还是读数口径在解析摩擦下失效**，如实记录。

### 4.5 墙

**墙是路线的属性，不是形状**——没有东西要在视口里拖，只有"哪一侧、从哪到哪、多高"。所以它是 **Track 节点上的导出数组**（`TrackWall` 资源），存在**关卡场景**里；只有外观参数（`wall_color` / `wall_thickness` / `wall_ramp`）进 cfg。

**没有墙的路段把横截面塌缩到路面边缘的一个点**，于是墙是**从路面里长出来的**，而不是旁边突然冒出一个带自由边的薄片——后者在高速下是个能绊住球的坎。两端各 `wall_ramp` 米渐变。

⚠️ **完全塌缩的路带必须直接不发**：那些零面积三角形若进了碰撞网格，**Jolt 会挂死整个场景**（构建毫秒级完成、物理五分钟不动）。

### 4.6 失败判定

球的位置**低于赛道轨迹的最低点减去 `fall_margin`** 即判定掉落。用代码判定而不是 `Area3D`：赛道是程序化生成的，铺一张"底下的触发体"既费事又容易和赛道重叠。

## 5. 赛道生成

> **Phase 1 实际落地（2026-10-10）**——与原设计相比**刻意裁剪**，用户拍板"先保证不触发边界情况就行"：
>
> - **赛道 = `Path3D`**，其 `curve` 指向 `resources/tracks/track_01.tres`（一个 `Curve3D`）。`scripts/track.gd`（`class_name RaceTrackPath`）沿曲线扫掠一个**等宽矩形截面**成 `ArrayMesh` + `ConcavePolygonShape3D`；宽度 / 厚度 / 采样数 / 颜色走 cfg `[track]`。**§5.3 的编辑流程就是最终形态，没有变。**
> - ~~**`RaceTrack` / `TrackSection` 资源暂缓**~~——**多条赛道已引入**（§5.7，用的精简版 `RaceTrackInfo`：只带路由与墙）。**分段变宽 / 半管 / 窄桥仍未做**，全库赛道等宽（`half_width` 是全局 cfg）。
> - **生成期曲率校验暂缓**：改为**造赛道时用一次性脚本核算最小转弯半径**。`track_01` 实测 **38.2 m**，对半宽 3.0 有 **12.7 倍**余量，够不着折叠。
> - **赛道清单（§5.4）与起终点标记（§5.5）随多赛道一起做**。
> - ⚠️ **一条实测的坑**：`ConcavePolygonShape3D.backface_collision` 默认是 `false`，面**只沿法线一侧碰撞**。扫掠的三角形绕序反了的话，路面就变成一个球会直接掉进去的薄壳——第一次生成就是这样，球在行驶中陷进路面 0.57 m。**绕序必须让法线朝外。**

### 5.0 路面扭转与相机平面（2026-10-12 重写；原文是"外倾由曲率推导"）

⚠️ **这一节整个被推翻过。** 原文让外倾**由曲率推导**，现在**撤掉了**——理由见下面第二条。原文留下的四条教训仍然有效，附在末尾。

**现在**：路面绕前进轴的扭转角**逐点写在路径点上**——`make_track.gd` 的 `"tilt"`（单位度）或 `"aim"`（一个世界方向，工具解出所需的 tilt）。cfg 的 `bank_max` / `full_bank_radius` / `bank_deadband` 三个键连同它们的读取代码一起删掉了。

- **为什么撤掉自动外倾**：它**不可编排**。竖直回环的曲线框架本身就会绕着前进轴转几百圈（下一条），而从曲率推出来的外倾只会跟着一起转——它没有任何地方可"瞄"。用户实机报的"第一个环后半段扭转角度不对"，根因就在这儿。
- ⚠️ **`Curve3D.tilt` 是现成的，但有个反直觉的地方**：实测给两个控制点设 0°→90°，采样框架确实绕前进轴转了 90°。但本版本（4.7.2）里 `sample_baked_with_rotation(offset, apply_tilt, cubic)` 的 `apply_tilt` **传 true 和传 false 输出完全一样**——tilt 数据**无条件生效**。代码里一直传 `false`，而四条赛道的 tilt 全是 0，所以至今没暴露。**别以为传 false 就能关掉它。**
- ⚠️ **符号：以实机为准，探针暂时不可信**（2026-10-12）。探针测出来是"**正值抬左边缘**"（平路沿 −Z、`+20°` 时左边缘比右边缘高 2 m），据此把左弯做成"右边缘高、左边缘低"。**用户在实机里看到的正好相反**，而我**没能找出探针错在哪**——扫掠的 `_slab_ring` 与探针读的是**同一个 `frame`**、用的是同一段 `Vector3(-3,0,0)`，本该一致。所以当前四个弯的外倾方向是**按眼睛定的**：`make_track.gd` 的注释里写了"别按探针改回去"。**这条待查。**
- ⚠️ **tilt 是相对曲线框架的，而框架自己会转**。环的两条腿侧向错开 7 m（那是为了避免自交），代价是曲线带上挠率：沿第一个环采样，框架**自己**累计侧倾 **+116°**——而一个竖直平面内的圆本该是 0°。所以"该写多少度"要先知道框架歪了多少，于是有了下面的 `"aim"`。
- **`"aim"` 更接近作者真正想说的话**：与其写"这里转 47 度"，不如写"路面朝那儿"。工具有解算器：设 tilt → 采样 → 量出法线还差多少 → 减掉，迭代 8 轮（相邻点的 tilt 会互相渗入，一轮不够）。
  - ⚠️ **手填 tilt 试过两轮，两次都错**：缺口最大到 80 多度，而且**符号与直觉相反**。换成 `"aim"` 一次就精确命中——控制点上的法线逐位等于写进去的方向。
  - ⚠️ **解完之后必须"展开"tilt 序列**（2026-10-12 补）。tilt 存的是**原始角**且**线性插值**，而解算器每轮独立求解、结果被包在 ±180° 里：螺旋上出现过 `-3.02 rad → +2.97 rad` 这种相邻点，它们**是同一个转角**（差 2π），但插值会照着数字走——**扭 343° 再扭回来**，每圈两个可见的结。`_unwrap_tilts()` 把每个角压进"邻居的半圈之内"就解决了。⚠️ **加减整圈不改变框架**，所以这一步放在解算之后是安全的。
- ⚠️ **加密环上的控制点会让事情变糟**。从 8 点加到 16 点，最小转弯半径从 **9.1 m 掉到 6.0 m**——正好等于路宽，路面边缘开始自折叠；因为 Catmull-Rom 的自动切线在密集点上开始抖。**改环上的点数必须回头看那个数。**
- ⚠️ **长直线接到紧螺旋上会甩出一个急弯**。手柄长度按各自间距缩放，40 m 的来路紧接 6 m 一格的螺旋段时，接缝处最小转弯半径掉到 **1.7 m**。修法是**用间距渐变的过渡点**（12 m 一档），不是加密。
- **相机限位跟着赛道平面**（cfg `[camera] align_distance` / `align_damp`）：球**离路面**近于 `align_distance` 时，相机的工作平面阻尼过渡到该处路面的法线；**滞空**之后过渡回世界向上。**转向基用的是同一个 up**。
  - ⚠️ **判据是"沿法线的余量"**（2026-10-12 修了**两轮**，值得记）。第一版比"到**中心线**的距离"，而球坐在路面上时那个数就是**一个球半径**——阈值写 8.0、实际读 0.5，**永远够不着**，这条从来没生效过。第二版改成 `三维距离 − 半径`，**仍然是错的**：球在路面平面内**横向**跑得越快，这个值涨得越像高度，于是**环上最先炸**——实测球绕环一圈，420 帧里 **394 帧被判成滞空**，平面整段被按回世界向上，而那正是最需要它跟住路面的一处。**最终版比的是沿法线的分量** `(球 − 路面点)·法线 − 半径`：球被钉在法线方向一个半径处，**横向怎么跑都不影响它**。**实测**：绕环全程 `clearance` 稳定在 **−0.002 ~ −0.004 m**，平面从 **+0.95 平滑翻到 −0.62**，一次都没误回正。
- **球的 `surface_normal` 也来自同一处**（`race.gd` 每帧只查一次 `frame_near`，喂给球与相机两边）。**平路上这一切与世界向上完全等价**，是**验过**的：改前改后驱动都是 27.0 m / 16.54 m/s。

**原文（自动外倾）留下的四条教训，仍然有效**：

1. ⚠️ **曲率公式我一开始写错 2 倍**：用的是前后各 `BANK_STEP` 的朝向差，那跨过的是 `2·BANK_STEP` 的距离，却只除以了 `BANK_STEP`。
2. ⚠️ **外倾符号是量出来的，不是推出来的**。第一版**28 个弯道采样全部倾反**（路面朝外倾，正好把球甩出去）。判据：**弯道内侧那条边必须是矮的那条**。
3. ⚠️ **曲率估计必须有平滑窗口**。Catmull-Rom 过稀疏路径点的曲率本身摆动很大，照抄曲率会让路面**搓板式扭转**；症状很有迷惑性——球在**几乎平坦**的地方"停不稳"。
4. ⚠️ **`frame_near` 必须返回倾斜后的坐标架**。第一版返回的是 `sample_baked_with_rotation` 的原始结果，于是外倾对球和相机**完全无效**。

### 5.6 起点与终点（2026-10-10 追加）

按 §5.5 的原案，**不额外建实体节点**。做法是**把它们画进路面的顶点色**：

- 扫掠时每个路环按它在曲线上的位置取一个颜色（`start_t` / `finish_t` 附近若干环取标记色，其余取路面色），材质开 `vertex_color_use_as_albedo`。
- 一个路带整段取一个颜色（取起始环的那个），所以色带的边界正好落在环边界上，而不会在两环之间渐隐。
- **起终点各是一个 `Area3D` 判定框**（横跨路面的薄盒），**真的进去才触发**：越过起点线的那一下**才开始计时**（在那之前时钟不跑，所以一局是从线上开始算、不是从按键开始算），进入终点框才结算。**不是**"位置超过某个数"。
- **终点后方有缓冲区**：一段 24 米的延伸路面（`runoff_length`，cfg `[play]`）加一块挡墙。没有它，高速冲过终点的球会直接飞出世界——那读起来像游戏把它扔了，而不是赢了。
- **缓冲区两侧默认带空气墙**：沿延伸路面两侧各一段**不可见**的实体挡板（`RailLeft` / `RailRight`，高 `RAIL_HEIGHT`，`track.gd` 里常量），**不挂在 `[` 键上**。`[` 的空气墙是拿来救一局的，而缓冲区已经不再是"一局"——它是球**本来就该停下**的地方，从旁边滑出去既不是玩家干的、玩家也补救不了。挡板内侧面正好落在半宽处，与路面边缘齐平。
- **结算后路面继续支撑**：`FINISHED` 把球的 `frozen` 换成一个新的 `coasting` 标志——**保留道路支撑与接触摩擦，只拿走驱动**。`frozen` 会把地面一起拿走（它本来就是靠跳过 `_integrate_forces` 来钉住球的），球于是**从它刚越过的路面里沉下去**。实测：越过终点后球始终稳定在**恰好一个半径（0.5000 m）**上方；被侧向推开时应停在 **2.4975 m**（挡板内侧面 3.00 − 半径 0.50 = 2.50 的上限内），而单靠摩擦它本该冲到约 3.06 m 掉下去。
- **过线演出**（cfg `[celebration]`）：相机绕球慢转一圈（**期间接管偏航，鼠标不算数**——胜利圈不归鼠标管）、屏幕两侧喷彩纸、**淡黄色冷烟花**——终点线两侧一对，**外加沿缓冲区两侧铺满全长的一条**（`emission_shape = BOX`，一段发射体盖住整条边；长度取自赛道而不是写死的数）。烟花位置全部取自**赛道的坐标架**而不是写死坐标，赛道改形它们跟着走。
  - 冷烟花的"自发光"用 `shading_mode = UNSHADED` 表达，**不是 `emission`**：粒子靠顶点色渐变淡出，而 emission 不乘顶点色，开了 emission 粒子会在生命末尾**硬切消失**。颜色走 `Gradient_spark`（`#FFF2A8` 系，与终点色带 `FFD24A` 同一族）。
- 额外好处：标记与扫掠**不可能失同步**——它们本来就是同一批顶点。

⚠️ 路径点清单留在 `scripts/make_track.gd` 里（造赛道的工具，见文件头）。它**不是**一次性脚本：曲线也可以在编辑器里拖控制点改，但那份清单是"路径点为什么在这里"的唯一记录。

### 5.7 多赛道（2026-10-11 追加）

**一条赛道 = 一份 `RaceTrackInfo` 资源**，`track_index.tres` 列出全部四条。加赛道的同时把"赛道是什么"从场景挪进了资源：

- **路由与墙住在 `RaceTrackInfo` 里**（`curve: Curve3D` + `walls: Array[TrackWall]`），**不再写死在场景里**。理由：球、相机、HUD、起终点与缓冲区都是**结构**，每条赛道一模一样；**只有路不一样，而路是内容**。内容进资源——这正是 §5.1 说的"`RaceTrack` 资源暂缓，等需要多条赛道时再引入"：现在就是那个时候，只是引入的是这个精简版。
- **一个场景跑全部赛道**（`scene_path` 每条仍填同一个 `race.tscn`，留作"某条赛道真要换家具"的出口）。`race_root` 把整行交给关卡，关卡在 `configure()` **之前**把 `curve` / `walls` 装到 `Track` 上——`configure()` 就是建路的那一下。
- **代价（刻意接受）**：`race.tscn` 单独打开跑不起来（没有曲线，`_build()` 会 `push_error` "no curve assigned"）。**同一个事实只留一处**，比在场景里再抄一份 track_01 的曲线和墙、然后改一处漏一处要好。
- ⚠️ **踩过的坑**：`RaceSettings` 的键是**逐条手写**的，往 cfg 里加键却忘了加进读取表**不报错**——静默用兜底值。`spark_run_amount` 就这么栽过一次。**改 cfg 就要改 `race_settings.gd`。**

**四条赛道的性格**（都由 `make_track.gd` 的路径点清单烘出来，清单是"路径点为什么在这里"的唯一记录）：

| id | 名字 | 形状 | 最小转弯半径 | 最小自接近距离 |
| --- | --- | --- | --- | --- |
| `track_01` | 第一赛道 | 缓 S：直道 → 宽左弯 → 宽右弯 → 直道，两个弯各外倾 ±15° | 38.2 m | 37.0 m |
| `track_02` | 第二赛道 · 螺旋 | **轴线沿前进方向的圆柱壁，绕 2 圈（720°）的螺旋线**：半径 6 m、每弧度前进 8 m | 15.1 m | 27.9 m |
| `track_03` | 第三赛道 · 双回环 | 120 m 助跑 + **两个 20 m 高的竖直回环（球在顶上倒挂）**，环面法线瞄向环心 | 9.1 m | 6.2 m |
| `track_04` | 第四赛道 · 发夹弯 | 五个交替急弯（各外倾 ±22°），弯与弯之间地面上下错 9 m | 11.9 m | 35.6 m |

- **半径是硬约束**：扫掠在**转弯半径 < 半宽（3.0 m）时内边缘会自交、网格翻面**。（§5.2 要求的生成期校验仍未做——现在是 `make_track.gd` 每次生成**打印**最小半径，靠人看。）**必须远大于 3.0。**
- ⚠️ **半径不能只看路径点**：Catmull-Rom 在关节处共用切线，**急弯路线的实际半径比路径点看上去小得多**——第一版"连续弯"（振幅 ±17 / 间距 40）量出来只有 **13.4 m**：20 m/s 过弯要 3g，而抓地只有 1.2g，**球必然滑出去，这关是过不去的**（该赛道现已被 $track\_04$ 取代，教训不变）。**改完路径点必须重跑生成器看那个数。**
- ⚠️ **第二个数：最小自接近距离**（2026-10-12 新增）。球的"路在哪"用的是 `get_closest_offset`（**全局最近点**），**道路与自己并行时它没有答案**——螺旋的两圈、回环的两条腿，都是"并行"。生成器现在**同时打印这个数**，判据是**必须明显大于 6.0 m（两倍半宽）**：低于它就是两条路真的叠在一起。（`track_03` 的 6.2 m 是贴着这条线过的。）
  - 实测：螺旋 37.5 m、双回环 6.2 m 都还在安全区内；**但把回环改成沿前进方向错开时，这个数掉到 0.4 m**——见下。
- ⚠️ **重复路径点会把曲线静默弄坏**：`_direction()` 取前后点之差作切线，两个点重合就得到零向量，Catmull-Rom 拿到零长度手柄后**在关节处折返**——最小半径当场掉到亚米级，而路径点清单看上去完全正常。生成器现在**直接 `push_error` 拒收**。
- ⚠️ **回环的"能过"取决于相机那一侧**（2026-10-12 订正）。原文写的是"回环只能攒速度、踩油门没用"——**那是当时的相机造成的**：转向基是只有偏航的平面，所以竖直路段上前进输入投影为零。相机改成跟随行驶方向之后，**油门在竖直路段上有用了**（§6），回环不再非要靠进环速度。
  - 但**环高仍然有个上限**，只是它现在由"驱动能不能克服重力"决定，而不是由进环动能决定：环上净加速度 = `摩擦上限 − 重力` = `μ·(g + k·v²) − g`。按当前值（`friction 1.2`、`downforce_coefficient 0.01`）球在环底静止起步时约 **1.96 m/s²**，爬 20 m 的环够用，但**起步很肉**。地上的极速仍是 **23.4 m/s**（阻尼卡住的，不是 `max_speed` 的 34）。
- ⚠️ **回环的两条腿只能侧向错开，而且错开量要小**。一个闭合的回环画成单条曲线只有这一条路可走：
  - 两腿**合成一个点** → 曲线在环底折返（自交）；
  - 两腿沿**前进方向**错开 → 环的两半**落到彼此身上**（同一高度的两点在路程上同处、相距 0.4 m，实测）；
  - 两腿**侧向**错开 7 m → 可用，但它让**路面扭转**（曲线不在一个平面内），球会被侧向甩；错开越多扭得越狠。7 m 是"躲开 6 m 路宽"与"少扭一点"两条约束刚好都满足的位置。
- **墙只立在直道上**：现役四条赛道各在开局直道与收尾直道立一段。弯道的内外之分要看弯的方向，**看不出来就别赌**——立错一侧就是陷阱。
- **验证（headless 探针，没开窗口）**：算法是**把球贴着路面放**（沿路面法线抬高 0.02 m）而不是从上方扔下去——**"扔下去"对回环无效**：球被放在环的侧面时，"上"是水平方向，重力根本不会把它拉向路面。贴面放置后跑 150 帧，四条赛道全程 **`above` = 0.5000**（恰一个半径）。另外把球以 30+ m/s 放在回环底部任其绕行，**能一路贴到接近环顶**，证明解析地面在倒挂段同样接得住。

### 5.1 数据模型（`class_name RaceTrack extends Resource`）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `String` | 关卡标识，存档的键（§7） |
| `display_name` | `String` | 选关界面上的名字（中文） |
| `curve` | `Curve3D` | 路径（内置三次贝塞尔资源） |
| `sections` | `Array[TrackSection]` | 沿曲线的分段属性 |
| `start_t` / `finish_t` | `float` | 起点与终点在曲线上的参数位置 |

`TrackSection`（`class_name TrackSection extends Resource`）：`t0` / `t1`（参数区间）、`half_width`（半宽）、`bank_deg`（外倾角）、`rail`（有无护栏）、`profile`（横截面类型：平路 / 半管 / 窄桥）。

### 5.2 生成器（`class_name TrackBuilder`）

沿曲线按 `Curve3D.bake_interval` 采样，每个采样点用 `sample_baked_with_rotation(t)` 取位置与朝向（**含外倾**），铺一圈横截面顶点，`SurfaceTool` 逐段成面 → `ArrayMesh`。

**横截面必须有厚度**（§4.2 第 3 条）：路面下方要有一层"基座"几何，让球即使钻到边缘也还有实体可撞。

**生成期校验（必须有，同 07-breakout 关卡校验器的做法）**：**转弯半径 < 半宽**时，扫掠出的内边缘会自交、mesh 翻面。这必须在生成时 `push_error` 报出**是哪一段、哪个参数越界**，并拒绝生成该赛道。**静默生成一个翻面的赛道比直接报错糟糕得多**——玩家看到的是"球莫名其妙飞出去"。

⚠️ **仍未做**：`make_track.gd` 目前只**打印**最小转弯半径，**不拒收**；而收窄（下一条）之后，"半径 < 半宽"已经**不再等于**"会折叠"了，所以那条判据本身也需要重想。

### 5.2.3 `P` 里的球体读数（2026-10-13 加）

⚠️ **`P` 是一个开关，不是四个**。赛道那边（碰撞线框 + 中心线）和关卡这边（参考系方盒 + 三支箭头）**必须同时起落**——它们都是"对同一局运行的读数"，**只显示一半的开关比没有开关更糟**。实现上：`track.gd::toggle_debug()` 在**赛道**那一半上切，关卡**读回状态**再照着设自己那一半；⚠️ **不要自己记一份镜像标志**，那正是第一版把两边设成**相反**的原因（切完又取了一次反）。

`P` 打开时，球身上另外画三支箭头，外加方盒变色：

| 读数 | 颜色 | 缩放 | 来源 |
| --- | --- | --- | --- |
| 速度 | 绿 `6BFF8F` | 0.15 m 每 (m/s) | `linear_velocity` |
| 施加的扭矩 | 红 `FF6B6B` | 0.3 m 每 (N·m) | `ball.applied_torque` |
| 除支撑外的外力 | 蓝 `6BB5FF` | 0.15 m 每 (N) | `ball.applied_force` |

- ⚠️ **扭矩与力此前根本没有被记录下来**——打完就丢。要画先在 `ball.gd` 里存成 `applied_torque` / `applied_force`，并且**每步开头清空**（一个陈旧的读数比没有读数更坏）。重力在开头就记进去，其余各处累加。
- **零矢量不画**（而不是画一个点），所以不动的读数不会在屏幕上留垃圾。
- **方盒在"滞空"时变橙**（`FF9A3C`）：那是参考系**被托住而不是被跟随**的唯一状态，也就是"盒子显示的"与"路面实际做的"分家的唯一状态。
- 三个缩放是**各配各的**：速度、扭矩、力三个量级差得远，共用一个系数会让其中一支短到看不见。


### 5.2.2 `P` 叠加层里的赛道中心线（2026-10-13 加）

**按 `P` 除了画碰撞线框，还画出赛道自己的中心线**（青色 `4BD3FF`，沿法线抬高 0.05 m 以免被路面吞掉）。

- 它和旁边的碰撞线框**不是一回事**：**线框是墙，中心线是路线**。一个弯看着不对时，这两样一起看才能分清**是路线错了还是路面错了**。
- 它是**代码生成**的（`_centerline_mesh()`），不放进场景——它是"对曲线的一遍读数"，而**曲线恰恰是场景里没有的东西**。
- 与碰撞线框**同一个开关**（`toggle_debug()` 同时切两者），因为它们属于同一类东西：**只读的显示**。


### 5.2.1 急弯处收窄内侧边（2026-10-12 加）

**比路宽还急的弯，会把内侧边缘往回扫进自己身上**——曲面折叠、网格翻面、球掉下去。**收窄那个弯的内侧**就是出路，而真实道路本来也这么修：发夹弯的内侧是路肩，不是全宽。

- **判据**：该点的侧向曲率（`_lateral_curvature()`，符号即"哪边是内侧"）→ 曲率半径 `1/|κ|` → 内边缘到弯心的余量 = 半径 − `INNER_MARGIN`(0.8 m)。
- **收窄量**：余量 ≥ 半宽就不动；否则内侧缩到 `(_half_width − 余量) / _half_width`。**数学保证内边缘到弯心始终 ≥ `INNER_MARGIN` > 0**，即不越过弯心、不折叠。
- **路面与墙用同一处计算**（`_inner_narrowing()` / `_edge_x()`）——护栏必须立在路面**实际有的**那条边上，而不是"全宽时本该有的"那条边。
- ⚠️ **验证的限度**：造了一条**半径 1.3 m**（远小于 3 m 半宽）的测试路线，生成器能出图、不报错。**但没有读回网格顶点去证明它真的没折叠**——目前的保证是**数学上的**，不是测出来的。真实急弯上的集成验证仍欠着。
- ⚠️ **它现在还没被真正用上**：四条赛道最急的弯是 9.1 m，离触发点（半宽 + 1.4 m）还远。它的存在是为了**允许以后把弯做得更急**（比如正在缩小的螺旋）。

### 5.3 编辑流程

赛道**在 Godot 编辑器里拖控制点**——但有一个必须记住的坑：

> ⚠️ **`Curve3D` 自己的 Inspector 编辑器是 2D 的**（只画 X/Y 平面），拿它编一条 3D 赛道会非常难用。**正确做法是把 `race.tscn` 里的 `Track`（`Path3D`）的 `curve` 指向 `resources/tracks/track_01.tres`**——这样打开 `race.tscn` 就能在 3D 视图里拖点，改动直接落到那个 `.tres` 上。

### 5.4 ⚠️ 赛道清单（教训 37 的同型风险）

选关界面要列出所有赛道。**不许扫 `res://` 目录**——那正是"本地跑得好好的、导出版空手而归"的原型（教训 37 / 39，`.txt` 与 `.cfg` 都栽在这上面）。

用一份**显式的清单资源** `resources/tracks/track_index.tres`（一个持有 `Array[RaceTrackInfo]` 的资源，每行带自己的路由与墙，见 §5.7），选关界面读它。这样每条赛道都被**引用**，因而必然被打包进构建。

`.tres` 属于资源、`all_resources` 应该带上——但**按老规矩，导出后仍要在包里验一遍**（教训 37 的教训就是"以为是资源"）。

起点与终点**不额外建实体节点**，由 `TrackBuilder` 依据 `start_t` / `finish_t` 在赛道网格上刻出高对比色块。

## 6. 相机（`camera_rig.gd`）

- **第三人称跟随**：rig 的理想位置 = 球位置 + 一个随速度轻微后拉的偏移；实际位置用阻尼 `lerp` 逼近——**不加阻尼的话高速下相机会把球甩出画面**。
- **参考系跟赛道方向**（2026-10-12 改定）：基准 = **up 取路面法线、forward 取这条路在这一处的走向**（`track.forward_near()`）。**视角固定在这个基里**，只有一个固定的俯仰角（cfg `pitch`）——**鼠标不参与**（2026-10-14，DECISION_LOG 087）。
  - ⚠️ **这个基同时就是转向基**，所以它改的不只是观感——**这才是"回环过不去油门"的解法**。竖直路段的路面平面**包含世界上下**，一个"世界前方"的输入投影上去约等于零，回环只能靠进环时带的速度滑过去。改成跟道路方向后，前进输入**按构造**落在路面平面内。**实测**：球停在环的侧面按前进，先被重力拽下 3 m，随后稳住并回升（速度 1.28 → 2.41 m/s），`frame` 的前方确认为沿环向上。
  - ⚠️ **跟的是"路的走向"，不是"球的速度"**（这一条改过两轮）。跟速度时，竖直路段上**重力才是速度的主人**：球在环上滑行时"前进"会变成"原路退回"。当时的补丁是"速度偏离路面超过 60° 就用路面方向"——**而直接取路面方向把这个补丁整个消掉了**：那个 60° 判据、`heading_min_speed`、以及"低速时保持上一帧"全部删除。
  - **路面方向不能盲信**：赛道靠近自己时，最近点查找可能交回**另一段**的切向（方向**相反**）。符号取自当前 heading 已经指的那一侧。
  - **飞行（`]`）与胜利圈必须冻结跟随**：飞行靠相机的完整轴，跟着走会把相机的偏航反馈进 `look_basis`，让飞行**自己转向**。
  - ⚠️ **首帧直接对齐，不做阻尼**：从世界 UP 起阻尼到一处竖直路面，会拿**错误的平面**去 seed 朝向；而与它 edge-on 的方向摊平后是**零向量**，落进兜底值就卡死（实测卡在 −Z）。
- **视角固定沿赛道方向**（2026-10-14 起）：相机在这个基里**不动**，唯一的自由参数是俯仰角 cfg `pitch`。⚠️ **鼠标控制整块是被拿掉的，不是被解决的**——相机的重新设计一直没做，这是让项目先往前走的临时口径（DECISION_LOG 087）。
  - 被拿掉的做法（2026-10-12–10-13 期间在用）：`InputEventMouseMotion` 直接读、改基里的偏航与俯仰，**俯仰限位**（`pitch_min` / `pitch_max`，不允许翻过头顶）。三个 cfg 键连同读取表一起删了。
  - ⚠️ **代价记在这里**：`]` 飞行模式的推进方向取自**相机自身的轴**（`look_basis`）。视角固定后它仍然沿赛道前进方向，但**含一个固定的向下俯角**（`pitch` 越大越向下），玩家**不能再靠抬头瞄准爬升**。飞行键本身仍然可用、仍然能跑完全程。
- **相机相对转向**：键盘的二维输入在**这个基**上解算（屏幕里按"左"球就往屏幕左转）。这是 3D 竞速的标准做法，也是这台相机存在的理由。
- 相机**不跟随球的旋转**——球在滚，视野不该跟着打转。**跟随的是平动**，这两件事不是一回事。
- **不穿墙、不穿路面**（2026-10-12 加）。⚠️ **两样东西会挡路，而只有一样能射线检测**：护栏是**真碰撞体**，路面**完全没有**（它是解析约束，§4.4）。所以护栏走射线，路面靠"相机不得低于**球所在平面** `MIN_ABOVE`"。
  - ⚠️ 该下限必须用**球所在的平面**（`_wanted_up`），不能用**相机阻尼后的 `_up`**：螺旋上两者能差很多，拿滞后的那个量做判据，相机就正好待在它要躲的路面底下。
  - ⚠️ 而且要在**缓动之后**再应用一次——阻尼位置只是"在去的路上"，而路上仍然穿在路面里。
- **每次重开相机直接落位**（`snap_to_target()`，不走缓动）：以前每局开头都要从上一局的落点滑过来，而"靠滑到位"的距离不算距离。
- ⚠️ **试过一版"第一人称"，当天就删了**：只把眼位挪到球上、参考系原样不动。**那不是要的东西**——用户的判断是"参考系没改，那算了"。留在这里是因为**它标记了一条分界线**：把眼睛挪到球上不等于第一人称，**真正要变的可能是参考系本身**（相机该**独立于赛道**地决定朝哪看）。**相机控制整块正等着一次重新设计**——2026-10-14 先把鼠标拿掉、改成固定视角顶上（见上），设计本身仍未开始。
- **⚠️ 环顶的"倒挂"是世界系里的，不是屏幕上的**（2026-10-13 澄清，措辞在更早的记录里是错的）：球在环顶时法线朝下、相机在世界里是头朝下的，**但屏幕上的球—路相对关系与平地完全一致**（路面照样从屏幕下方伸向深处、球照样压在路中央），因为**相机跟着一起倒**。这是这个参考系的设计意图（"坐在车里的司机"），**不是待修的缺陷**。
  - **实测**（2026-10-13，headless 探针驱动真实 rig，外倾扫 −180°→+180° 共 25 点）：**方盒的 up 在屏幕上的滚转恒为 0.000°**；同一列里**地平线滚转 ≈ −外倾**（±180° 处读 ∓180.0°）。两个数同时成立 = "世界里倒着、画面里看不出异常"。
  - ⚠️ **有一处会把世界方向暴露出来**：`race.tscn` 用的是**程序化天空**（`background_mode = 2`，`sky_top_color` 深蓝 / `ground_bottom_color` 近黑，上下分明）**加一盏带阴影的 `Sun`**。这两样**不跟参考系走**，环顶时会在屏幕上翻过来。**球和路本身没问题**（球是纯色 `SphereMesh`，任何朝向都一样）。**"环顶看上去和普通地面一样"这个说法只在没有天空参照时成立**——要不要去掉天空的方向感，是"环顶该无感还是该刺激"的口径问题，**未定**。
  - ⚠️ **还欠一个数**：heading 的**稳态滞后** ≈ （速度 ÷ 转弯半径）÷ `heading_damp`，按现有四条赛道是 **6°–24°**；而 §33 记的 `track_03` **87.8°** 按这个公式对不上（该是 20° 出头），**疑为旧参数或瞬态值，用之前要重量一遍**。
- ⚠️ **朝向的半圈翻转：那句"符号取自当前 heading"的尺子是错的**（2026-10-13 修）。它原本用 `road.dot(_heading) < 0`，**只要夹角超过 90° 就翻转**。而 heading 是**限速**追着赛道走的（`heading_max_turn`），球在急弯快跑时赛道转得比限速快、heading 正常地落在后面——**一过 90° 就被自己的安全检查翻掉半圈**。这就是"第四关第三个弯必定旋转 180°"（延迟＝限速追不上，翻转＝那把 90° 的尺子）。
  - **两处一起改**：阈值从 90° 放到 **120°**（`dot < -0.5`，只有明显反向才翻转）；`heading_max_turn` 2.5 → **6.0**（它必须高过"赛道在球底下转多快" = 速度/半径；全库最急 11.9 m，30 m/s 时是 **2.5 rad/s**——旧值正卡在临界，所以永远差一点）。
  - **实测**（数学模拟全速跑完全程）：`track_04` 最大滞后 **21°**、`track_01` **5.9°**、`track_03` **87.8°**，**符号检查在三条赛道上各触发 0 次**。
  - **教训**：**"超过直角就算反向"是个会在最坏时刻发作的判据**——真正反向的东西接近 180°，而正常滞后轻易就能过 90°。
- **球身上画一个半透明的方盒**（`race.gd::_build_frame_box()`，节点名 `BallFrame`），**它显示的就是这个参考系**（up = 路面法线、forward = 赛道方向、随路面翻转）。**没有任何碰撞**，它是一张"计算的图"，不是个东西。形状是**扁的板**（1.7 : 0.8 : 1.7），不是立方体——从后面看立方体各个面都一样、读不出朝向，而贴在路面上的板一眼就能看出它朝哪。**默认隐藏，挂在 `P` 上**（与碰撞线框同一类东西：都是"读数的显示"，都不改变玩法）。
  - ⚠️ **它必须用未缓动的参考系**（`camera_rig.get_frame()` 读 `_wanted_up`），**不能用相机缓动后的 `_up`**：螺旋上两者能差 10° 以上，用后者画出来的盒子会**脱离路面**——而盒子一旦脱离路面，它就在显示错的东西。
  - ⚠️ **基必须正交，否则盒子会被"压扁"**（2026-10-12 查实）。`_frame_of()` 里的 forward 是**投影到"当时那个平面"**上得到的，而平面本身在缓动，两者一起用的时候可能差几度——**一个轴不严格垂直的基不是旋转，它带缩放**，施加到网格上就是把盒子压扁（看着像"盒子可压缩"，其实盒子是刚的）。修法：**先把 forward 对 up 摊平再到单位长**。实测修复后**轴长误差 0.000000、轴间点积 0.000000**。
  - 之所以值得画：**球是球体，没有"正面"**——任何朝向看起来都一样，所以"视角跟随的方向"无法从球身上得到，只能从路面算出来。**一个决定整个游戏观感、却完全看不见的东西，正是该画出来的那种东西。**

## 7. 存档（`save_store.gd`）

**⚠️ 这是全库第一次引入存档**——01–09 一处都没有（各 `*_settings.gd` 只读 `res://` 的 cfg，不是写存档）。

- 位置 `user://marble_race.save`，格式 `ConfigFile`。
- 键：`best_time/<track_id>`（秒，`float`）。
- **健壮性（验收里逐条验）**：
  - 文件不存在（首次运行）→ 空存档，**不报错**；
  - 文件损坏 / 解析失败 → 回退空存档 + `push_warning`，**不崩**；
  - 存档里有一条**版本号**，版本不符 → 回退空存档（而不是拿旧数据硬套）。
- 存档只在**破纪录时**写，不在每帧写。
- **本作不需要 `include_filter`**：存档是运行期写进 `user://` 的，不存在打包问题。（赛道 `.tres` 见 §5.4。）

## 8. 像素化与 CRT（`shaders/crt.gdshader`）

- `SubViewport` 内部尺寸 **640×360**（cfg `internal_width` / `internal_height`），`SubViewportContainer.stretch = true` 铺满，`texture_filter = NEAREST`。
- **MSAA 必须关、TAA 必须关**——开着会把边缘抹平，像素感直接消失。
- `crt.gdshader` 挂在 `SubViewportContainer` 的 `ShaderMaterial` 上，采样那张画布，三件套：
  - **扫描线**：周期**必须锁到内部像素行的整数倍**，否则会和像素网格打架出 moiré 波纹；
  - **桶形畸变**：轻微，UV 外扩的部分按黑处理（标准 CRT 圆角感）；
  - **暗角**：轻微。
- **不做色差**：低分辨率下色差会把画面糊成一团。
- cfg 里 `[pixels] enabled` 可**整体关掉**（阶段 0–3 调试时关掉，见 §11）。

## 9.5 关卡循环

`race.gd` 的状态机，四个状态：

| 状态 | 行为 | 出口 |
| --- | --- | --- |
| `READY` | 球被**钉在起点**，计时归零，显示 `SPACE TO START` | 空格**或任意方向键** → `RUNNING` |
| `RUNNING` | 计时；每帧查两个条件 | 掉出赛道 → `FALLEN`；进度 ≥ `finish_t` → `FINISHED` |
| `FALLEN` | 停 `restart_delay`，显示 `FELL - RESTARTING` | 计时到 → `READY` |
| `FINISHED` | 球**滚出缓冲区**（切 `coasting`：保留支撑与摩擦、不再接受驱动）、放演出、停 `finish_pause`，显示 `FINISHED <时间>` | 计时到 → `READY` |

- **压线用"钉住"，不是 `freeze`**：`freeze` 会停掉 `_integrate_forces`，而收不到该回调的刚体是驱动够不着的（也就是"力没有施加上去"那个坑）。所以是用一个 `frozen` 标志跳过驱动 + 每帧把位置写回起点。
- **出发也接受方向键**：方向盘式的"按空格确认"在赛车游戏里是多一道手续——油门本身就该能起步。
- **空格在 `RUNNING` 里是刹车**，形式是**恒扭矩**（`brake_torque`，反向于自转）叠在**滑行阻尼**上。用户要的是"力度随转速降低而增强"——**阻尼在数学上做不到这个方向**：它每秒拿走固定**比例**，所以刚按下最猛、快停下几乎不动。恒扭矩每秒拿走固定**量**，球越慢、同样的力占剩余速度的比例越大，最后一段收得快。刹车**压过油门**（本作的转向输入就是油门，二者无法同时要求）。
  - 实测（同一入速 20.4 m/s）：松手滑行 **8.08 s / 56.7 m**；按住空格 **2.5 s**。
- **起终点画在路面的顶点色里**（§5.6），判定是**横跨路面的 `Area3D` 判定框**——越过起点线那一瞬才开始计时，真的进终点框才结算（原案的"投影进度"已废弃）。

## 11. `Esc` 分层（本作对项目级约定的局部修订）

CLAUDE.md 的键位约定写的是"`Esc` = 返回 hub"，但那是给**没有内部菜单**的游戏定的。本作有多层界面，因此：

| 当前在哪 | `Esc` 做什么 |
| --- | --- |
| 主菜单 | `GameRouter.back_to_hub()`（与既有约定一致） |
| 选关界面 | 回主菜单 |
| 关卡中 | 打开暂停菜单（**暂停物理**） |
| 暂停菜单 | 继续（关掉暂停菜单） |

**只有主菜单那一层碰 `GameRouter`**——关卡与选关界面都不得直接调 `back_to_hub()`（它们够不着 hub，只能逐级退）。这条要在 DECISION_LOG 里记一笔，因为它是**对项目级约定的修订**。

## 14. 验收

### 可自动校验的（headless）

- `godot --headless --path . --import` 无 error / warning；`MarbleRace*` / `RaceTrack` / `TrackBuilder` 等全局类全部注册。
- 场景可加载、无脚本错误。
- **赛道生成**：三角形数 == 采样点数 × 横截面段数 × 2（可数）；起点终点落在 `start_t` / `finish_t`；**构造一条转弯半径越界的赛道，生成器必须 `push_error` 并拒绝**。
- **物理（Phase 0 的量化结论固化下来）**：给定 `spin_torque`，稳态线速度落在预期区间；**松手后球在有限时间内停下**（不是永动）；把球以 `max_speed × 1.5` 射向一块薄板，**不穿过去**（这条钉的是 CCD）。
- **存档**：文件不存在 → 空存档不报错；写入 → 读回一致；**拿一段垃圾字节当存档 → 回退空存档且不崩**；版本号不符 → 回退空存档。
- **失败判定**：球落到 `fall_margin` 之下 → 触发重开，计时清零。
- 调试叠加层用**像素计数**证明关得掉（该颜色别处不出现，同 09 的做法）。

### 只有人能定的

- 手感：加速 / 极速 / 转向响应 / 坡的增速感——**Phase 0 与 Phase 2 之后逐项试**。
- 观感：像素化强度、CRT 三件套的力度、HUD 清晰度与像素化的取舍。
- 赛道：一条赛道的长度、弯道密度、护栏位置。
- 听感：滚动声随速度的变化是否可辨。

### 导出后必做（教训 37 / 38 / 39）

- **重新导出前先重启 Godot 编辑器**（编辑器会把内存里的导出预设写回磁盘，覆盖手改的 `include_filter`）。
- 导出后**在包内查 `resources/tracks/*.tres` 是否真的在里面**，再实机跑一趟。**只跑本地永远发现不了这类问题。**
