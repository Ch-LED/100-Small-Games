## 3. 结构模型（场景即架构，CONSTITUTION 五点五）

### 3.1 入口与切屏

`tetris.tscn` 的根是 `Node`（`tetris_root.gd`），管三屏：**主菜单 / 棋盘 / 结算**。切屏是**整屏替换**，与 `10-marble-race`、`11-pinball` 同构。

```
TetrisRoot (Node)                 tetris_root.gd —— 模式 / 切屏 / 跨局的成绩
├─ ScreenHolder (Node)            ← 主菜单、棋盘或结算，同时只留一个
├─ OverlayLayer (CanvasLayer)     ← HUD 与暂停菜单常驻
├─ Audio (Node)                   tetris_audio.gd
└─ Save (Node)                    tetris_save.gd（常驻，跨屏）
```

### 3.2 一局的场景 `scenes/play.tscn`

**静态骨架写进场景**——棋盘、侧栏、每一个槽位都是显式节点。代码只往里填数据。

```
Play (Node2D, play.gd)                    ← 这一局的**驱动**：规则、重力、锁定
├─ Playfield (Node2D, playfield.gd)       ← **画**：棋盘、落点投影、边框、侧栏
│   ├─ Ghost (TileMapLayer)               ★ 落点投影（同色的空心 tile，默认隐藏）
│   ├─ Board (TileMapLayer)               ★ 10×20 可见区，set_cell 填
│   ├─ Frame (Line2D)                     棋盘边框（四个角点由 setup() 按格宽算）
│   ├─ SidePanel (Node2D)                 Hold 槽 + 5 个 Next 槽
│   │   ├─ Hold (TileMapLayer)            4×4 格，scale 0.5
│   │   └─ Next0 … Next4 (TileMapLayer)   4×4 格，scale 0.5
│   ├─ DebugLayer (Node2D, tetris_debug.gd)  P 叠加层：网格 / 生成线 / 包围盒 / 读数
│   └─ Effects (Node2D)                   ← Phase 4：清行闪白、顶死抖动
├─ Stats (Control, hud.gd)                ← 棋盘**左侧**的读数（§6.5）
└─ Keymap (Node, tetris_input.gd)         ← 键位 → 本作的语义动作（§7）
```

⚠️ **读数在棋盘左边，不在右边**：右边已经被 Hold 与 5 个 Next 槽占满（近 500 px），再塞四行数字会贴到屏幕底边。左边是空的，于是 SCORE / LEVEL / LINES / TIME / 判定行放那儿——**两边各管一件事，谁也不挤谁**。

⚠️ **`Ghost` 必须排在 `Board` 之前**（在它下面）：它的 tile 是同色的**空心**描边、内部透明。画在实心层**之上**的话，描边颜色与方块本体相同，会被方块盖住——等于没画。放在下面，它在深色底上是个清楚的框，而实心块自然把它遮住。

⚠️ **预览槽缩到 `scale = 0.5`**：一个 4×4 槽按 32 px 格算是 128 px，五个竖排要 640 px，装不下。缩一半后每槽 64 px，Hold 加五个 Next 不到 500 px。**0.5 是整数比**，像素仍然对齐（一格像素变 2×2 屏幕像素），不会糊。

⚠️ **根是「驱动」、子节点是「视图」，这个方向是刻意的**。Godot 里**子节点的 `_ready()` 先于父节点跑**，所以父节点（`Play`）在 `_ready()` 里访问 `$Playfield` 时，子节点的 `@onready` 引用**已经就绪**。反过来放就得等一帧才能拿到 `Board`。`Play` 因此可以放心地在 `_ready()` 里 `_field.setup(_settings)`。

⚠️ **`Board` 是 `TileMapLayer` 而不是一堆 `ColorRect`**——CONSTITUTION 五点五点名"地图用 `TileMapLayer`（配 `TileSet` 资源）"。它的 `tile_set` 由代码在 `setup()` 里赋值，理由见 §8。**节点本身是场景里显式建的**，程序化的只是图集。

**到 Phase 1 为止落了 `Play` / `Playfield` / `Ghost` / `Board` / `Frame` / `SidePanel`（含 `Hold` 与 `Next0–4`）/ `Keymap`**，其余按阶段追加——调试层 Phase 3、特效与预览槽的标签 Phase 4。

## 4. 纯逻辑层

四个脚本都是 **`extends RefCounted`、`class_name` 注册、完全不碰场景树**。这样规则能被 headless 直接断言（`09-lights-out` 的 `grid_model.gd` 是同一条口径）。

### 4.1 `tetromino.gd`（`class_name Tetromino`）

**形状与朝向的唯一来源。**

- 七种方块 `enum Kind { I, O, T, S, Z, J, L }`（顺序与 §6 表格一致，索引即 `Kind`）。
- 每种方块用**包围盒**表示：`J L S T Z` 用 3×3，`I` 用 4×4，`O` 用 2×2。
- **四个朝向不手写，由包围盒绕中心旋转推出**：朝向 0 的格子清单写死在表里，朝向 R / 2 / L 由旋转算法生成。
  - 理由：手抄 28 组坐标是 28 次抄错的机会；旋转算法只需写对一次，而且**"绕盒中心转 90°"这件事本身可以被断言验**（转四次回到原位、每朝向恰好 4 格）。
- `cells(kind, rotation) -> Array[Vector2i]`：包围盒内的格子坐标（y 向下，左上为 `(0,0)`）。
- `spawn_offset(kind) -> Vector2i`：出生时包围盒左上角落在棋盘的哪一格。**I 与其它不同**（4×4 盒比 3×3 盒高一格），O 也不同——这是规范规定的出生位置，不是随手定的。
- `kick_table(kind, from_rot, to_rot) -> Array[Vector2i]`：踢墙偏移，见 §5。

### 4.2 `piece_bag.gd`（`class_name PieceBag`）

- **7-bag**：把七种方块洗成一袋，按序发出；袋空了再洗一袋。
- `next() -> Kind`、`peek(n) -> Kind`（看接下来第 n 个，供 Next 队列显示）。
- `remaining() -> Array[Kind]`：当前袋里还没发出的（只给 `P` 叠加层读数用，不参与玩法）。
- ⚠️ **不是纯随机**。7-bag 意味着**最坏情况下也不会连出三个同种方块**，而这正是"俄罗斯方块是随机的"这个直觉的反面。**后来者看到"怎么老是这几种轮流来"不要去"修"它**——这是标准。
- 袋内洗牌用**独立的 `RandomNumberGenerator`**，种子可在 cfg 固定（调试用）。

### 4.3 `tetris_board.gd`（`class_name TetrisBoard`）

**棋盘与消行。没有"当前方块"的概念**——那是 `TetrisPlay` 的事。

- 尺寸 `WIDTH = 10`、`TOTAL_ROWS = 24`、`VISIBLE_ROWS = 20`、`SPAWN_ROWS = 4`。
  **行 0 在顶**（Godot 惯例），**行 4–23 是可见的 20 行**，行 0–3 是生成区（方块出生与踢墙的空间，**不绘制、不参与消行**，但**参与碰撞**）。
- 内部状态就是一个 `Array[PackedInt32Array]`（每行 10 格），0 = 空，1..7 = 锁定方块的 `Kind + 1`。**存颜色索引而不是布尔**，因为渲染要按块上色。
- `is_free(cells) -> bool`：一组格子是否全在界内且为空（**负行不算越界**，那是生成区）。
- `can_place(kind, rotation, origin) -> bool`、`lock(kind, rotation, origin)`。
- `clear_lines() -> int`：移除所有满行，上方整体下落，返回消掉的行数。**消除的行是"全部满行"，不是"从下往上遇到的第一批"**——中间被掏空的行照样消。
- **`t_spin_corners(kind, rotation, origin) -> int`**：以方块**包围盒中心**的四角为观察点，返回被占（越界或已锁）的角数，以及**"尖所指方向的两个角"里有几个被占**。这是 T-spin 判定的几何依据（§6.2）。
  - ⚠️ **四角是包围盒的四角，不是方块格子的四角**。T 的包围盒是 3×3，中心格 `(1,1)`，四角是 `(0,0) (2,0) (0,2) (2,2)`——**中心那一格永远是 T 自己占着的**，所以要从盒的四角看，不能从"方块的格子"看。
- **没有 `is_top_out()`**：顶死的判据是**新方块在出生位置放不下**，由 `play.gd` 在 `_spawn()` 里用 `is_free()` 直接判。这样"生成区"就不必参与判定，行 0–3 只剩两个用途——踢墙的余地、以及绘制时裁掉的部分。

### 4.4 活动方块与锁定延迟（在 `play.gd` 里，不是独立类）

活动方块就是 `(kind, rotation, origin)` 三元组，加三个计时状态：

- `lock_timer`：落地（不能再往下）后开始累加，`>= lock_delay` 则锁定。
- `lock_resets`：**落地时**（`_is_grounded()`）成功的移动 / 旋转 +1 并清空 `lock_timer`；**达到 `lock_reset_cap` 后不再重置**。半空中的移动不算——那时计时器本来就没在跑。
- `last_action`：`NONE / MOVE / ROTATE / DROP`，**T-spin 判定只认 `ROTATE`**（§6.2）。

⚠️ **重置上限是必须的**。没有它，玩家可以靠无限旋转把方块永远吊在顶上（社区管这个叫 *infinity*），游戏就结束了。规范给的上限是 **15 次**。

## 5. SRS（旋转与踢墙）

### 5.1 旋转

- 朝向 4 个：`0 / R / 2 / L`（顺时针）。
- 旋转即"包围盒绕中心转 90°"（§4.1）。
- `O` 的四个朝向完全相同，**转了等于没转**，且**不踢墙**。

### 5.2 踢墙

旋转后的目标位置若被占，按踢墙表**依次尝试 5 组偏移**，第一组不碰撞的生效；**5 组全失败则这次旋转不发生**（不是"强行转进去"）。

⚠️ **踢墙表只覆盖单步 90° 旋转**（0→R、R→0、R→2、2→R、2→L、L→2、L→0、0→L，共 8 组），**没有 0→2 这种两级跳**。游戏里的旋转永远通过 `rotation_step()` 走一步，所以那 8 组就够了；`_published_kicks()` 遇到不存在的行会 `push_error` 并降级成"只试原地"，而不是静默用错的数据。

⚠️ **踢墙表的 y 轴方向和本作相反**：SRS 规范定义 **y 向上为正**，而本作棋盘 **y 向下**（§4.3）。所以 §5.3 的表是**规范原值**，代码里必须**逐条把 y 取反**后再存。
- **这不是可以"顺手"的地方**：漏取反一个不会报错，而是**某个特定朝向的踢墙静默失效**——玩家会在某个角度转不动，而代码里看不出任何异常。
- 取反只做一次，做在 `tetromino.gd` 的 `kick_offsets()` 这一个函数里，**`KICK_JLSTZ` / `KICK_I` 两张表保留规范原值**，让"哪部分是规范、哪部分是我们的转换"一眼可辨。

### 5.3 踢墙表（规范原值，y 向上）

**JLSTZ**（四种共用一张）：

```
0 → R   (0,0)  (-1, 0)  (-1,+1)  ( 0,-2)  (-1,-2)
R → 0   (0,0)  (+1, 0)  (+1,-1)  ( 0,+2)  (+1,+2)
R → 2   (0,0)  (+1, 0)  (+1,-1)  ( 0,+2)  (+1,+2)
2 → R   (0,0)  (-1, 0)  (-1,+1)  ( 0,-2)  (-1,-2)
2 → L   (0,0)  (+1, 0)  (+1,+1)  ( 0,-2)  (+1,-2)
L → 2   (0,0)  (-1, 0)  (-1,-1)  ( 0,+2)  (-1,+2)
L → 0   (0,0)  (-1, 0)  (-1,-1)  ( 0,+2)  (-1,+2)
0 → L   (0,0)  (+1, 0)  (+1,+1)  ( 0,-2)  (+1,-2)
```

**I**（单独一张）：

```
0 → R   (0,0)  (-2, 0)  (+1, 0)  (-2,-1)  (+1,+2)
R → 0   (0,0)  (+2, 0)  (-1, 0)  (+2,+1)  (-1,-2)
R → 2   (0,0)  (-1, 0)  (+2, 0)  (-1,+2)  (+2,-1)
2 → R   (0,0)  (+1, 0)  (-2, 0)  (+1,-2)  (-2,+1)
2 → L   (0,0)  (+2, 0)  (-1, 0)  (+2,+1)  (-1,-2)
L → 2   (0,0)  (-2, 0)  (+1, 0)  (-2,-1)  (+1,+2)
L → 0   (0,0)  (+1, 0)  (-2, 0)  (+1,-2)  (-2,+1)
0 → L   (0,0)  (-1, 0)  (+2, 0)  (-1,+2)  (+2,-1)
```

**O**：无踢墙（只有 `(0,0)`）。

⚠️ **表里有多行是逐字相同的**（如 `R→0` 与 `R→2`）。这不是抄漏——SRS 就是这么定义的：**从同一个朝向出发时，顺转与逆转共用同一组测试**。看着可疑，但**不要"修"它**。

### 5.4 断言怎么验（不拿表验自己）

- **结构性质**：**每个单步旋转**（4 个朝向 × 2 个方向 = **8 组**，不是全部 12 组有序对）恰好 **5 个互不相同**的偏移；每条的第 1 个偏移**恒为 `(0,0)`**；`O` 只有 `(0,0)`。
- **已知场景**（真正值钱的部分）：
  1. **I 块在空棋盘上 `0 → R`**：第 1 组 `(0,0)` 就成功，**位置一格没动**；
  2. **T 块贴左墙朝 R、逆时针转回 0**：第 1 组越界、第 2 组 `(+1,0)` 生效，转完**恰好右移一格**——这就是"贴着墙也能转"；
  3. **5 组全失败时旋转不发生**：把棋盘填满得只剩 T 自己占的 4 格，断言 `rotation` 与 `origin` **原地不动**；
  4. **T-spin 局面**（Phase 2 补）：构造已知局面，断言角数报 3、且最后一步是 `ROTATE`。
- **朝向数据**：每个方块**每个朝向恰好 4 格、互不重复、全在包围盒内**；**逐级旋转的结果 == 手工把上一朝向转 90°**；`O` 四个朝向完全相同；`Z` 是 `S` 的水平镜像、`L` 是 `J` 的（这条**不依赖旋转代码**）；**T 的"尖"在 rot 0/1/2/3 分别朝上/右/下/左**（用几何方式识别尖——去掉它之后剩下三格共线——所以验的是 SRS 对形状的定义，不是验旋转代码自己）。

## 6. 计分、等级与重力

### 6.1 计分表

| 动作 | 基础分 | ×等级 |
| --- | ---: | :---: |
| Single（1 行） | 100 | ✓ |
| Double（2 行） | 300 | ✓ |
| Triple（3 行） | 500 | ✓ |
| **Tetris**（4 行） | **800** | ✓ |
| T-spin（无消行） | 400 | ✓ |
| T-spin Single | 800 | ✓ |
| T-spin Double | 1200 | ✓ |
| T-spin Triple | 1600 | ✓ |
| Mini T-spin（无消行） | 100 | ✓ |
| Mini T-spin Single | 200 | ✓ |
| Mini T-spin Double | 400 | ✓ |
| **Back-to-back** | 上一个动作也是 Tetris / T-spin 时 **×1.5** | — |
| **Combo** | 第 n 次连续消行 **+50 × n × 等级** | ✓ |
| Soft drop | **1 / 格** | ✗ |
| Hard drop | **2 / 格** | ✗ |

- ⚠️ **Tetris 是单行的 8 倍，不是 4 倍**——这是规范里最重要的一个不对称，也正是"攒四行再消"这个核心技巧的经济基础。别"顺手"改成线性。
- **Soft / Hard drop 的分不加等级倍率、也不进 combo / B2B**。
- **Combo 从第二次连续消行起计**：第一次消行是 combo 0（不给分），第二次 combo 1，第三次 combo 2……
- **B2B 适用于 Tetris 与全部 T-spin（含 mini）**；中间夹一次普通消行则 B2B 断开。
- 一次动作**可能同时命中多项**（如 T-spin Double 且 B2B 且 combo 3），分数**逐项相加**，顺序无所谓（都是加）。

### 6.2 T-spin 判定（本作里唯一"不是查表"的规则）

**三个条件同时成立才判 T-spin**：

1. **最后一步动作是旋转**（`last_action == ROTATE`）。移动或下落之后即使形状对得上也不算。
2. 方块是 **T**。
3. 包围盒中心的**四角里至少 3 个被占**（§4.3 的 `t_spin_corners`）。

在此之上区分 **full / mini**：

- **两个"尖所指方向"的角都被占** → **full T-spin**；
- 否则（只占了 1 个） → **mini T-spin**；
- ⚠️ **例外**：这次旋转用的是**第 5 组踢墙偏移**（最后那一组）时，**一律提升为 full T-spin**，不看角。这条是规范里有的，不是补丁。

⚠️ **没做到这一步的话，`last_action == ROTATE` 会把普通旋转也判成 T-spin**，分数虚高而且看不出来。三个条件缺一不可。

### 6.3 等级与重力

- **等级由累计消行数驱动**：`level = 1 + lines_total / 10`（向下取整）。
- **等级唯一的用途是查重力表与当计分倍率**，两者共用同一个 `level`，**不允许各算各的**。
- 重力表（`level` → **每格下落秒数**）：

| Lv | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| s/格 | 1.000 | 0.793 | 0.618 | 0.473 | 0.355 | 0.262 | 0.190 | 0.135 |

| Lv | 9 | 10 | 11 | 12 | 13 | 14 | 15+ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| s/格 | 0.094 | 0.064 | 0.043 | 0.028 | 0.018 | 0.011 | 0.007 |

- **表由公式现算**：`interval = (0.8 − (level − 1) × 0.007) ^ (level − 1)`，**取到 `level_cap`（cfg，初值 20）为止**，超过则保持 `level_cap` 的值。
- ⚠️ **下落用累加器而不是"每帧一格"**：`fall_accum += dt`，`while fall_accum >= interval: 下落一格; fall_accum -= interval`。低等级时一帧远不到一格，高等级时**一帧要落多格**——写成"每帧最多一格"的话，高级别的重力表就废了。
- ⚠️ **interval 有下限**（cfg `min_fall_interval`，初值 `1.0 / 60.0 / 20.0`）：到 20G（每帧 20 格）就封顶。再快没有意义，只会让 `while` 循环变长。

### 6.4 冲刺模式的计时

- 计时从**第一个方块出生**开始，到**第 40 行被消除**那一帧结束。
- 计时**不含**暂停时间（暂停时累加器不推进）。
- 成绩格式 `mm:ss.mmm`。

### 6.5 最近的判定要能被看见

侧栏 `Stats` 里有一行 `EventValue`，每次锁定后显示**这一次做了什么**：`SINGLE` / `DOUBLE` / `TRIPLE` / `TETRIS` / `T-SPIN DOUBLE` / `MINI T-SPIN SINGLE`……既没消行又不是旋转就是空。名字由 `TetrisScoring.describe()` 生成（纯函数，可断言）。

**为什么单开一行**：T-spin 是**唯一一种"分数会跳、但没有任何东西告诉你为什么跳"**的得分。玩家打出一次 T-spin 之后，除了"分数好像多了不少"之外**没有任何确认手段**——而"我到底打出来没有"这件事，靠猜是学不会的。**把它写出来，这个技巧才可学。**（用户实机后的原话是"我的技术不足以让我打出 T-spin"——所以这一行同时是给玩家的确认，也是唯一能在实机上验证 T-spin 的途径。）

## 7. 输入

### 7.1 项目级键位 → 私有语义（本作确立的项目约定）

**`project.godot` 的 `[input]` 只管"哪个键"，不管"这个键是什么意思"**。语义由每个游戏自己翻译——这样同一个 `Z` 在 RPG 里是"确认"、在动作游戏里是"攻击"、在本作里是"逆时针旋转"，而项目级只维护一份键位表。

本作新引入了三个**纯键位动作**（无语义）：`key_z`、`key_x`、`key_c`。它们与既有的 `wasd_* / arrow_* / fire` 一样，只回答"这个键被按下了吗"。**后续项目要用这三个键，必须先看这里的约定**（已记入 `CONSTITUTION` 五之补充）。

### 7.2 语义动作层（`tetris_input.gd`）

`TetrisInput` 在 `_ready()` 里用 `InputMap` 注册本作私有的**语义动作**，事件从项目级键位动作**复制**而来（`action_get_events` → `action_add_event`），`_exit_tree()` 里移除：

| 私有语义动作 | 键位来源 | 含义 |
| --- | --- | --- |
| `tetris_move_left` | `arrow_left`, `wasd_left` | 横移 |
| `tetris_move_right` | `arrow_right`, `wasd_right` | 横移 |
| `tetris_soft_drop` | `arrow_down`, `wasd_down` | 软降 |
| `tetris_hard_drop` | `fire`（空格） | 硬降并立即锁定 |
| `tetris_rotate_cw` | `key_x`, `arrow_up`, `wasd_up` | 顺时针旋转 |
| `tetris_rotate_ccw` | `key_z` | 逆时针旋转 |
| `tetris_hold` | `key_c` | 暂存 |

- ⚠️ **事件是"复制"不是"引用"**：`InputMap` 没有"别名"机制，所以必须把键位动作的事件逐个 `action_add_event` 到语义动作上。`_exit_tree()` 里 `erase_action` 清干净。
- **语义名带 `tetris_` 前缀**，与全局动作区分开，也避免与未来别的游戏的私有动作撞名。
- 全局三键（`P` / `[` / `]`）与 `Esc` **不走这一层**，它们是项目级约定，语义在项目内已经固定。

### 7.3 DAS / ARR（规范留白，必须实机调）

- **DAS**（Delayed Auto Shift）：按住横移键后的**起始延迟**，之后才开始连续移动。
- **ARR**（Auto Repeat Rate）：开始连发后的**每格间隔**。
- 实现：按住时 `das_timer` 累加，超过 `das` 后每 `arr` 移一格；`arr = 0` 时表示**一帧移到底**（瞬时到位，是常见的高手感配置，cfg 里保留这个可能）。
- ⚠️ **松手要立刻清零**，且**左右同时按住时以最后一次按下的方向为准**（不然两个方向互相抵消，方块卡住不动）。

## 8. 渲染（`playfield.gd` + `tetris_tiles.gd`）

### 8.1 TileSet 由代码生成

`TetrisTiles.build() -> TileSet`：程序绘制一张 **7×1 的图集**（每格 32×32 px），七个方块各一格，**绘制内容 = 底色 + 内描边 + 左上高光**（§8.2），然后包成 `TileSetAtlasSource` 返回。

- ⚠️ **为什么 TileSet 是程序生成的**：本项目「零外部素材」的口径下，图集本身是画出来的，没有 `.png` 可以引用，所以 `.tres` 也无从存起。**程序化的只是图集，节点本身（`TileMapLayer`）是在场景里显式建的**——CONSTITUTION 五点五要求的"用 `TileMapLayer` 而不是一堆 `Sprite2D`"完全满足。
- **棋盘与所有预览槽共用同一份 TileSet**（同一个 `source_id`）。
- 图集用**最近邻过滤**，像素风的边框和高光才不会被插值糊掉。

### 8.2 一块格子长什么样

**实心块**（图集第 0–6 列）：

```
┌────────────┐   底色：该方块的 Guideline 标准色
│▓▓▓▓▓▓▓▓▓▓▓▓│   左上高光：底色提亮一档，占两条内边
│▓┌────────┐▓│   内描边：底色压暗一档，绕一圈
│▓│        │▓│
└─┴────────┴─┘
```

**落点投影**（图集第 7–13 列）：同色的**空心**描边、内部完全透明。它与实心块**共用同一张图集、同一个 `TileSet`**，只是取不同的 atlas 列（`atlas_coords()` / `ghost_coords()`）。

- **纯色块看不出体积**——加一道高光才有"这是一块砖"的感觉，这是 01–11 都没有的新需求（那些都是纯色块）。
- ⚠️ **落点投影默认不显示**：`Ghost` 节点在 `play.tscn` 里 `visible = false`，由 `P` 打开（§12.1）。它不是棋盘的一部分，是一层读数。
- ⚠️ **投影做成 tile 而不是用 `_draw()` 画**：它跟着方块每帧移动，用 tile 就只是 `set_cell`，批处理交给引擎；用 `_draw()` 则要自己算屏幕坐标、自己管重绘时机。既然图集本来就是代码画的，多画七格空框几乎不要钱。
- **消行闪白**（Phase 4）仍走 `Effects` 上的 `_draw()`——那是一段一闪而过的整行动画，不是常驻的格内容，做进图集反而别扭。

### 8.3 坐标映射

- 逻辑棋盘 **10×24**（§4.3），`TileMapLayer` 只画**可见的 20 行**。
- `layer_coords = Vector2i(board_x, board_y − SPAWN_ROWS)`。
- 生成区（行 0–3）里的方块**不上屏**——它在棋盘顶之上，本来就该看不见。但**AABB 与 Ghost 的计算走完整 24 行**，两者的差异只在这一处映射上。

## 12. `Esc` 分层与全局三键

### 12.1 两个开关：`Q` 管落点，`P` 管为什么

**它们是两个独立的开关，因为它们服务于两个不同的时刻。**

**`Q`（`tetris_toggle_ghost`）—— 落点投影**：当前方块直落到底的那四格，用同色的**空心** tile 画在棋盘层**之下**（§8.2）。**这是玩的时候看的**：我这一下会落在哪。

**`P`（`debug_toggle`）—— 只读叠加**：下面的东西都是**想"为什么"的时候看的**。
- 棋盘的**格子网格**（暗色细线）。
- **可见区顶部那条生成线**：在这条线以上的方块还在踢墙用的缓冲里。
- **活动方块的包围盒**（亮黄 `#FFE94A` 线框）与**中心十字**——**T-spin 的角判定看的就是这个盒的四个角**，所以能看见它就等于能看见"为什么这一转算/不算 T-spin"。
- 活动方块**逐格描边**。
- 四行读数：方块与朝向 / 当前重力间隔 / 锁定剩余与重置次数 / 7-bag 剩下什么。
- ⚠️ 开关**必须"出去也重绘"**（`_draw` 的绘制命令会被画布缓存），照抄 `03-pacman/scripts/pacman_debug.gd` 的带 setter 写法（DECISION_LOG 029）。

**为什么落点投影算"只读"而不是玩法**：它画出来的东西，玩家看一眼堆的高度就能自己推出来——它不增加任何**能力**，只是把已经可推的信息画出来。这与 `08-twenty48` 的 `P` 画四方向可行性、`03-pacman` 的 `P` 画幽灵寻路是同一条口径。

**默认状态：`Q` 的落点投影是开的，`P` 的叠加层是关的**（`DECISION_LOG` 094）。两个默认值不同是有意的——**投影是玩法的一部分**（Guideline 的标准体验里它常驻，一个下落中的方块本来就该让你看见它要落在哪），**叠加层是读数**。曾经把投影也默认关过一阵，那是错的。

⚠️ **`Q` 走的是"项目级键位 + 私有语义"那一套**（§7.1）：`project.godot` 里只登记 `key_q` 这个**键**，`tetris_toggle_ghost` 是本作自己的语义动作（`DECISION_LOG` 092）。`P` 不在此列——它是**约定动作**，语义在全项目固定。

### 12.2 `[`（作弊）——时间膨胀

- 重力间隔与锁定延迟**各乘 `[cheat] time_scale`（初值 3.0）**。落得慢、来得及想、来得及挪。
- HUD 的等级读数旁标 `SLOW`。
- **不复位任何东西**，只是把两个时间参数放大——所以关掉就是精确还原（乘的是 cfg 基准值，不是当前值）。

### 12.3 `]`（超级作弊）——零重力

**拆掉这个游戏最根本的那条约束：方块不再自行下落。**

- 开启后**重力项整个停用**——`fall_accum` 不再推进，方块停在玩家放手的那个位置，放多久由玩家定。
- **其余操作全部照常**：左右移动、旋转、软降（`↓` 主动下落一格）、硬降（空格直接落底并锁定）。**只有"时间"这一维被拆掉了**，方块本身该守的规矩一条没少。
- **落点投影与锁定延迟照常工作，且不需要专门写代码**：方块停在半空时根本"落不了地"，锁定倒计时自然不启动；软降到底或硬降才进入锁定流程——因为这两件事本来就是"还能不能再往下"的函数，而重力只是**主动去凑**这个条件的一个来源。
- **方块整块变荧光绿 `#00E676`**（不是标记某一格）——被接管的是方块的下坠。
- ⚠️ **开关的两个瞬间都要清空 `fall_accum`**：关掉重力的那段时间里累加器一直在涨，恢复的那一帧会**一次性下落几十格**（`while` 循环把它欠的账一次还清）。开启时也清一次，避免状态残留。
- **每局开始 / 重开时复位**（与项目约定一致）。

⚠️ **为什么是零重力而不是 AI**（本设计一度是"自动落块 AI"，被用户否掉）：重力是俄罗斯方块**最根本的约束**——整个游戏就是与下落赛跑，拆掉它既更轻松、又有趣，而且**顺手把调试也变简单了**：能把方块停在任意位置去验证消行与 T-spin 判定，不必等它自己落下来。**自动化属于"想不出别的花样"的游戏**（解谜 / 音游），本作不是——这条原则已写进 `CONSTITUTION.md` 八。

### 12.4 分层

- `Esc`：主菜单 → hub；游戏中 → 暂停菜单（`RESUME` / `RESTART` / `QUIT TO MENU`）；暂停菜单 → 继续；结算 → 主菜单。
- **暂停时树真的暂停**，菜单节点设 `process_mode = WHEN_PAUSED`（跟着一起暂停的菜单是谁也按不动的）。
- **暂停时 root 不处理输入**（它没设 `WHEN_PAUSED`），由暂停菜单自己接管 `Esc`——分层因此**不需要在 root 里判断"我在不在暂停中"**（`11-pinball` 已验证这条）。

| **Phase 2** | **计分系统**：计分表、**T-spin 三角判定**（full / mini / 第 5 组踢墙的提升）、combo、back-to-back、等级曲线、重力表接上、冲刺计时与结束条件；**Ghost 改挂 `P`、默认隐藏**。**已由用户实机验收（2026-10-14）**（顺带修掉软降跳格，见 §14 第 10 条） | 逐条对照 §6 的计分表；等级与速度对得上；冲刺消满 40 行结束 |
| **Phase 3** | 主菜单（模式选择 + 两个记录）、暂停菜单、结算卡、存档、`Esc` 分层、三个全局键、`P` 叠加层、音效。**已由用户实机验收（2026-10-14）** | §15 的人可验证项全过；两个记录退出重进还在 |
| **Phase 4** | **教程模式**（五关，§16）：固定开局 + 固定出块 + 过关判定 + 讲解卡；**落点投影改绑 `Q`**（§12.1）；消行闪白与顶死抖动的手感打磨 | 每一关都能被它的目标走法打通（断言强制）；导出版实测通过（教训 38/39：`.cfg` 是裸文件，必须 `include_filter="*.cfg, *.txt"`） |

**Phase 0 是唯一可以"先堆代码后重构"的阶段**；从 Phase 1 起每步都要落文档。

⚠️ **两条相对原计划挪了位置的**：
- **SRS 踢墙从 Phase 1 提前到 Phase 0**。它按目录契约本就属于 `Tetromino`（纯数据），而旋转不带踢墙时**贴着墙就转不动**，那样称不上"能玩"。Phase 1 因此只剩 Hold / Ghost / Next / 锁定重置 / DAS-ARR。
- **`soft_drop_interval` 进了 cfg**（初值 0.05 s/格），软降是按住连发，不是按一次一格——它和 DAS/ARR 不是一回事，后者的"长按重复"在 Phase 1 才做，那时两者会共用同一套计时思路。

⚠️ **Phase 0 的锁定是简化版**：固定的 0.5 s、**移动/旋转不重置计时器**。这是刻意的——重置加上限才是 Phase 1 的内容，而"不重置"本身没有 *infinity* 漏洞（§4.4），所以 Phase 0 不存在已知可挂的 bug。

## 14. 风险 / TODO

1. **⚠️ 踢墙表的 y 轴转换**（§5.2）——本轮最大的坑。表抄错或取反漏一个，表现是"某个角度转不动"，而代码里看不出异常。**必须靠 §5.4 的已知场景断言顶住**，不能只靠读代码。
2. **⚠️ T-spin 判定的三个条件缺一不可**（§6.2）。最容易犯的错是只判"最后一步是旋转"——那样普通旋转也加分，而且**分数虚高的表现是"打得莫名其妙地好"，不是崩溃**，很难被发现。
3. **⚠️ 锁定重置的上限**（§4.4）。不实现就是 *infinity* 漏洞：玩家可以无限转把方块吊在顶上，**游戏直接没法结束**。这条不算"锦上添花"，是必需品。
4. **⚠️ 重力累加器的写法**（§6.3）。写成"每帧最多落一格"会让高级别废掉——**这个 bug 只在等级高时才显形**，前几分钟的自测发现不了。
5. **⚠️ 本作没有"复刻对象"可以对照**。前 11 款里 11 有原作可玩、可以肉眼比对；这一款**只有一份文字规范**，而规范原文本轮没拿到（§0）。所以**规范符合性只能靠断言 + 用户实机**，而用户实机的判断依据是"玩过的官方版本手感想不想"——**这条要明说，不要把"我看代码觉得对"当成"符合规范"**。
6. **DAS / ARR 是纯口味**（它们也正是规范留白处，§7.3），必然要调，而且**玩家第一时间就会感觉到**。
7. **消行音的音数随行数变化**：四行时是四音上行，音长与间隔要压得住，否则 Tetris 的反馈会拖到影响操作。
8. **⚠️ 零重力下"游戏看起来像卡住了"**：方块停在空中不动，玩家若没注意到方块是绿的，会以为死机。所以**绿色标记必须够醒目**，且**开新局一定要复位**——不然下一局一开局就没有重力，玩家只会当成 bug。
9. **⚠️ T-spin 的断言验的是"摆出来的局面"，不是"打出来的局面"**。四条断言各自先把角占好再判，**能证明判定逻辑对，不能证明它在真实对局里真的会被触发**——而"从来没打出过 T-spin"这件事从分数上看不出来（只是分数偏低）。实机时要刻意试一次：把 T 转进一个凹槽，看分数跳的是 **800 还是 100**（`§6.5` 的判定行会直接把它写出来）。
10. **⚠️ 下落累加器被两种速率共用**（**2026-10-14 用户实机报"软降有时会在按下时下降相当大的距离"**）。`_fall_accum` 在重力下被允许累积到接近 `gravity_interval`（1 级时 1.0 秒），而**按下软降的那一帧间隔变成 0.05 秒**——欠下的 0.9 秒被 `while` 循环一次还清，**一下落 18 格**。
    - **修法**：检测到速率切换（软降按下或松开）就**清零累加器**；软降还额外在按下那一帧**立即落一格**，与横移的"按下即移"对齐。
    - ⚠️ **同类隐患要一起想**：任何"两个速率共用同一个累加器"的地方都有这个形状的问题。本作里另一个候选是 `_gravity_interval()` 随等级突变——但相邻等级的间隔变化很小，最多多落一两格，可以接受；**软降那种 20 倍突变才是要命的**。

## 15. 验收

### 可自动校验的（headless 断言套件）

- **方块数据**：每个方块每个朝向**恰好 4 格**；**转四次回到朝向 0**（逐格相等）；格子都在包围盒内；O 的四个朝向完全相同。
- **踢墙表**：§5.4 的四条结构性质 + 四条已知场景。
- **7-bag**：连抽 500 次，**每连续 7 个必然是七种的排列**；任意袋内**不出现重复**；`peek(n)` 与实际发牌顺序一致。
- **棋盘**：`is_free` 对四种越界情形（左 / 右 / 下 / 已占）都判不可放；**生成区（负行）不算越界**；`clear_lines` 消掉**所有**满行（含被掏空的中间行）、上方整体下落、返回正确行数；**没有满行时不动**。
- **计分**：逐条对照 §6.1 的表（含 Tetris 是单行 8 倍这条）；combo 从第二次起算；B2B 只在 Tetris / T-spin 后生效且被普通消行打断；drop 分不进倍率。
- **T-spin**（Phase 2）：§5.4 的已知局面**报 full**；构造一个 mini 局面**报 mini**；把最后一步换成移动**报"不是 T-spin"**；用第 5 组踢墙的局面**提升为 full**。
- **等级与重力**：`level = 1 + lines/10`；重力表与公式逐级对得上；**超过 `level_cap` 后不再变**。
- **状态机**：开局一袋、消行加分、等级上升、顶死进结算；冲刺**恰好 40 行结束**且计时正确；暂停不计时。
- **零重力（`]`）**：开启后**不按任何键，方块下落 0 格**（跑 300 帧断言 `origin.y` 不变）；按 `↓` 仍然逐格下落、按空格仍然落底并锁定；**关掉的那一帧方块只下落 1 格、不是几十格**（验证 `fall_accum` 被清空）；全程棋盘状态合法（无重叠、无越界）。
- **存档三态**：文件不存在 / 损坏 / 版本不符，三种都回退空存档且不崩；后两种能被界面读出来。
- `--import` 零 error / warning；`tetris.tscn` 与 `playfield.tscn` 可加载、无脚本错误；全部 `class_name` 注册成功。

### 只有人能定的

- **DAS / ARR 的手感**（这是规范留白处，也是最容易被玩家第一时间感觉到的地方）；
- **锁定延迟 0.5 s 的实际体感**，以及"挪够 15 次才锁死"会不会在实战里让人困惑；
- **踢墙的体感**：贴着墙转的时候是不是"该转得动就转得动"；
- **零重力（`]`）的手感**：方块停在空中时是不是真的"想放多久放多久"、绿色标记够不够醒目；
- **消行闪白与音效的节奏**——反馈快慢直接决定"能不能连起来打"；
- 界面排版：棋盘、Hold、Next 三者是否同屏可读、不打架。

### 导出后必做（教训 37 / 38 / 39）

- **导出前先重启 Godot 编辑器**，否则它会用内存里的旧预设覆盖 `include_filter`。
- 过滤器需要 `"*.cfg, *.txt"`——**`tetris.cfg` 是没导入器的裸文件**，本地跑得好好的导出版会静默用空配置。
- 导出后**在包内查 `tetris.cfg` 的内容**，并实机玩一局。

## 16. 教程模式

主菜单的第三项。五关，每关**一个手摆的开局 + 一个目标 + 一句讲解**。

### 16.1 为什么要有它

这款游戏里有几样东西**只看画面是学不会的**：Tetris 值单行的 8 倍、T-spin 能把一次普通的旋转变成 800 分、combo 是加在后面的。计分表能写进文档，但写不进玩家的手感。教程就是把这些局面**手工摆到玩家面前**——一次只教一件，做出来了才算过。

### 16.2 五关

| # | 教什么 | 开局 | 目标 |
| --- | --- | --- | --- |
| 1 | 消行与硬降 | 底行缺 2 格，给一个 O | 消掉 ≥1 行 |
| 2 | **Tetris** | 四行只缺一根一格的竖槽，给一个 I | **一次**消掉 4 行 |
| 3 | **T-spin** | 最左四列的一个 T 形缺口（`1100 / 1000 / 1101`，见 §16.7），给一个 T | 锁定判定为 T-spin |
| 4 | **Hold** | 手上是不合适的 O，但暂存槽里预存着 I | 用换出来的方块消行 |
| 5 | **Combo** | 两行各缺 4 格，给两个 I | 连续两次消行，中间不夹空锁 |

⚠️ **原定的第 5 关是 back-to-back，已换成 combo**。B2B 要求"连续两次 Tetris"，那需要一条很长的固定出块序列去堆两轮四行——**序列越长关卡越脆**（中途任何一步放歪，后面全废）。Combo 用同样短的局面就教会了"连着消有加成"，而且**实战里遇到得比 B2B 频繁得多**。取舍理由记在 `DECISION_LOG` 093。

### 16.3 数据（`tutorial_levels.gd`）

每关是一个 `Dictionary`：`title` / `hint` / `done` / `rows` / `pieces` / `demo` / `goal`，`hold` 可选。

- **`rows` 是手写的棋盘点阵**，`#` 是实心、`.` 是空，**顶行在前**，并且**贴底摆放**——这样只有一行的第一关也落在第 23 行，而不是飘在半空。
- ⚠️ **`rows` 里任何一行都不许是满的**。`clear_lines()` **不认"这是手写的"**——玩家一锁定任何方块，满行就被消掉，局面当场破坏，而目标从此达不成。**第 3 关最初就栽在这里**（底行铺了 10 个 `#`），表现是"一放就消、然后怎么都过不去"，画面上还看不出为什么。断言套件里有一条专门查这个。
- **`pieces` 是固定的出块顺序**。⚠️ **这条不能省**：靠 7-bag 抽的话，"教 Tetris"那一关可能根本不发 I 给你，教学就不成立了。序列**循环发**，免得玩家把脚本用完之后卡住。
- **`demo` 是开打前的演示**，一步一个动作（见 §16.5）。
- **`goal`** 是 `CLEAR_LINE` / `TETRIS` / `T_SPIN` / `HOLD_CLEAR` / `COMBO` 之一。

### 16.4 过关、放错与失败

- 教程屏**包着一个普通的 `TetrisPlay`**，只听它的 **`locked(lines, spin)`** 信号。**规则一点没改**——这就是为什么在这里学到的东西拿到实战里照样成立。
- 判定在 `TutorialLevels.is_passed()` 里，**纯静态、可断言**。
- ⚠️ **T-spin 那关是在"锁定"时判的，不是"转动"时判的**：转对了但没等它锁定，不算过。这是判定本身的定义（§6.2），不是教程的额外要求。
- ⚠️ **落错地方直接判失败并重开本关**（`TutorialLevels.is_solution()`）。局面是固定的，落错就没有"补救"可言——让玩家在一片已经走歪的棋盘上继续堆，只会让他不知道自己错在哪。判定**按格子的集合比**：换个朝向但占同样四格，照样算对（**这一关学的是位置，不是手指路径**）。
  - 对比的是**演示最后一步**的位置——所以 `demo` 的最后一帧同时就是"答案"。
- **顶死即重开本关**：局面是固定的，没什么可结算的，也没什么别的可做。
- ⚠️ **暂停菜单的 `RESTART` 在教程里是"重开本关"**，不是"从第一关重来"。一个卡在第三关的玩家要的是重来第三关；被扔回第一关不是他要求的。
- 过关后弹一句讲解，空格进下一关；第五关之后回主菜单。教程**不记成绩**。

### 16.5 演示：先看位置，再看按键

进关卡时**先跑一遍这一关要做的动作**，跑完才交给玩家。

- 每一步**分两拍**：先 `0.8 s` 显示**幽灵方块落在哪**，再 `0.8 s` 显示**按哪个键**。顺序是刻意的——**位置要在指令之前被看懂**，否则玩家只记住了一个键名，不知道往哪按。
- 演示期间**整局是冻结的**（`TetrisPlay.set_frozen()`），输入不响应。
- 演示的画面直接复用 `TetrisPlayfield.show_demo()`——和落点投影同一条绘制路径，所以"演示里的幽灵"和"玩的时候的幽灵"长得一模一样。
- ⚠️ 演示是 `await` 出来的，**换关或被重开时必须让它停下来**：每次载入关卡都递增一个令牌，协程每等完一拍就比一次，对不上就直接返回，免得旧演示回头去写新关卡的屏幕。
- ⚠️ **第 3 关的演示用"↓ 送到位"而不是硬降**：T-spin 要求**旋转是最后发生的动作**，而硬降会当场锁定——那一关的演示第一步必须说清楚这一点。

### 16.6 ⚠️ 每一关都必须在自动化里被打通

**手摆的局面一旦有 bug，玩家就是永远过不去——而画面上没有任何异常。** 所以断言套件里有两件事是硬性的：

1. **每一行都不能是满行**（§16.3）。
2. **逐关按演示的走法打一遍，断言过关判定真的为真**。

两道闸门各自抓到过一次真问题：
- 第 3 关最初只写了"转一下"而没让它锁定 → **报不可通关**（改的是测试，转向量不是完成）；
- 第 3 关的底行铺满 → **报有满行**（改的是关卡）。

**两个错误在画面上都一丁点看不出来。** 而且它们**互相独立**：满行存在时"可解"那条依然通过（因为它测的是"摆对位置会不会过关"，而满行是锁定之后才消的）——所以两条都得留。

### 16.7 T-spin 那关是怎么做出来的（2026-10-14，绕了一大圈）

**结论先写**：第 3 关是**真的 T-spin** 了，局面来自用户画的一个形状——**三行四列，`1100 / 1000 / 1101`**，摆在最左四列、贴底：

```
行21: ##..######
行22: #...######
行23: ##.#######
```

那条缝读出来是个 **T 形的缺口**。进去的走法是：

```
先顺时针转（竖起来）→ 左移两格 → 落到底 → 再顺时针转
```

**为什么必须"先转再落"**：缺口**开口只有两格宽**，而横着的 T 是**三格宽**。所以不能直落——**必须先转成竖的**才能进得去，到底之后再转横，最后那一转就是 T-spin。

### 为什么这件事绕了四轮

**⚠️ 一条本质事实**（值得单独记）：**T-spin 的位置永远不可能靠"直落"到达。** 槽的**上面两个角**必然落在下落中方块的**包围盒路径**上，而要判 T-spin 又要求那几个角被占。所以 T-spin **只可能发生在"底部的那一次旋转"**。这也解释了用户最初那句"必须连续按三下 z 才能钻进去"——转不进去是对的，**方向上得试**。

**⚠️ 更值钱的教训：我原来那条"每关可解"的断言是假的。**
它验证的是"把方块**摆到答案位置上**能否过关"——那是**瞬移，不是移动**。第 3 关的旧局面**通过了那条断言，却根本打不通**：T 从出生点落下停在 `(3,18)`，离"应该去"的 `(3,20)` 隔两行，而那个位置的上两角正好压在下落路径上。

**修法**：断言改成**从出生点出发、用玩家真有的动作**（转、横移、下落、暂存）把每关走一遍。改完**五关全红**——因为我连"**横移**"都没模拟（方块只会落在它出生的那几列）。补上横移后，1/4/5 关转绿，2/3 关仍红；这次的根因是**顺序写反了**（该"先转再移"，我写的"先移再转"）。三处一起修完，**五关全绿**。

**⚠️ 还有一层：描述一个局面比想象中难。** 用户先后给过三次形状，前两次（24 位的 6×4、加了 `0011` 的 7×4）我都**摆错了位置或读反了 0/1**——因为我一直在猜"这几列在棋盘的哪儿、外面是实心还是空"。**最后能成，是因为他把它简化到了三行、而且给了"在最左侧"这个位置信息。** 教训：**要用户描述棋盘局面时，让他给"整行 10 个数字、从下往上"，别让他画局部**——局部必然带来"贴在哪、外面是什么"两个额外未知数，而这两个未知数**没法从局部形状本身推出来**。
